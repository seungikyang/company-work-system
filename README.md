# Java 백엔드 취업 포트폴리오 워크북

사내 업무관리 시스템을 직접 설계하고 구현하면서 Java·Spring Boot 백엔드 취업에 필요한 결과물을 만드는 실습형 워크북입니다.

저장소를 내려받은 뒤 [`index.html`](./index.html)을 브라우저로 열면 6단계 HTML 학습 목차에서 목표 설정, 오늘의 학습, 직접 풀이, 프로그램 구현, 검증과 취업 증거 기록까지 순서대로 따라갈 수 있습니다. 오늘 볼 챕터를 고르면 해당 Hard·Starter·워크시트와 그 폴더에서 만들어야 할 취업 결과물·완료 검증이 바로 연결됩니다. 선택 챕터의 취업형 문제에 답을 쓴 뒤 힌트와 정답 기준을 개별 확인할 수 있고, 이전·다음 챕터로 00~39를 순서대로 이어갈 수 있습니다. 목표·답안·완료 표시·검증 명령과 결과는 현재 브라우저에 자동 저장됩니다.

## 프로그램 정의

이 저장소 자체는 완성된 사내 업무관리 애플리케이션이 아니라 취업 준비를 돕는 **워크북 프로그램**입니다. 사내 업무관리 시스템은 워크북에서 반복해서 설계·구현·검증하는 실습 주제입니다.

| 구분 | 의미 |
|---|---|
| 워크북 프로그램 | 목표 설정, 오늘의 학습, 5단계·40개 챕터 진행 체크, 챕터별 답안·힌트·정답 기준, 구현 가이드와 면접 준비를 제공하는 이 저장소 |
| 구현 대상 시스템 | 학습자가 별도 Spring Boot 프로젝트에서 완성할 직원·부서·휴가·공지·전자결재 시스템 |
| 최종 결과 | 실행 코드, 자동화 테스트, Git 기록, 포트폴리오 문서, 면접 답변 |

이 저장소의 목표는 빈칸 문제를 모두 푸는 것이 아닙니다. 아래 다섯 가지를 면접에서 설명할 수 있는 본인 프로젝트로 남기는 것이 최종 목표입니다.

- 실행 가능한 사내 업무관리 시스템
- 핵심 업무 규칙을 검증하는 테스트
- 구현 의도가 드러나는 커밋과 Pull Request
- README, ERD, API 명세, 트러블슈팅 문서
- 프로젝트 선택과 기술 설계를 설명하는 면접 답변

## 대상

- Java와 Spring Boot 기본 문법을 배운 뒤 포트폴리오 프로젝트가 필요한 사람
- CRUD를 넘어 승인·반려, 권한, 상태 전이, 트랜잭션을 연습하려는 신입·주니어 개발자
- SI·기업용 업무 시스템 백엔드 직무를 준비하는 사람

## 먼저 알아둘 점

`practice/starter/`와 `practice/hard/`의 Java 파일은 컴파일 가능한 완성 프로젝트가 아니라 핵심 로직을 직접 채우기 위한 코드 조각입니다. 정답을 복사해 제출하는 대신, 워크북에서 이해한 내용을 본인의 실행 가능한 Spring Boot 프로젝트에 다시 구현해야 합니다.

HTML 화면의 목표, 진행 상태와 챕터별 답안은 로그인이나 외부 서버 없이 현재 브라우저의 저장 공간에만 보관됩니다. 브라우저 데이터를 지우거나 다른 기기에서 열면 자동으로 이어지지 않으므로, 제출할 코드·테스트·커밋과 상세 증거는 본인 프로젝트와 [취업 준비 통합 워크북](./practice/job-preparation-workbook.md)에 함께 남깁니다.

## 시작 순서

1. [HTML 워크북](./index.html)에 목표 직무, 첫 지원 마감일과 하루 학습 시간을 적습니다.
2. 5단계 로드맵에서 아직 완료하지 않은 첫 단계의 안내 문서를 엽니다.
3. 오늘 끝낼 FR ID, 챕터 하나와 완료 조건 한 문장을 정합니다.
4. 선택 챕터의 취업형 문제에 핵심 책임·실패 조건·검증 방법을 먼저 적고, 막히는 만큼만 `1단계 힌트`를 엽니다.
5. Hard 또는 워크시트를 직접 푼 뒤 `정답 기준`과 Starter·상세 해설을 비교하고 빠진 내용을 보완합니다.
6. 표시된 결과물을 본인 프로젝트에 구현하고, 60분 체크 순서대로 실제 검증 명령과 실패·통과 결과를 기록합니다.
7. 답안 비교, 실행 결과물과 검증 증거가 모두 남았을 때만 완료로 체크하고 `다음 챕터`로 이동합니다.

한 번의 학습 세션은 `목표 선택 → 직접 풀이 → 실행 프로젝트 구현 → 검증 → 증거 기록` 순서로 끝냅니다.

## 챕터별 문제집 사용법

선택한 00~39 챕터마다 같은 문제집 패널이 표시됩니다.

1. 정답을 열기 전에 핵심 책임, 실패 조건, 검증 방법과 설계 이유를 내 답안에 적습니다.
2. 막히면 취업 결과물과 계층 책임을 연결하는 `1단계 힌트`만 확인합니다.
3. 직접 풀이 뒤 `정답 기준`을 열어 핵심 책임·구현 결과물·검증 근거가 답에 있는지 비교합니다.
4. 기술 키워드와 트레이드오프가 더 필요하면 [전체 정답과 해설](./practice/answers.md)을 엽니다.
5. 빠진 내용을 보완한 뒤 `내 답과 정답 기준을 비교했습니다`를 체크합니다.

답안과 비교 완료 기록은 챕터별로 유지됩니다. `새 학습 시작 · 오늘 기록만 비우기`는 오늘의 FR ID·챕터·완료 조건·검증 결과만 비우며, 목표·전체 진척도·문제집 답안은 보존합니다.

## 오늘 학습 검증 루프

1. 본인 프로젝트에서 반복 실행할 테스트 또는 빌드 명령 하나를 적습니다.
2. 실패하면 오류 메시지와 실패 입력을 기록하고 원인을 재현합니다.
3. 원인에 필요한 최소 코드만 수정한 뒤 같은 명령을 다시 실행합니다.
4. 통과하면 관련 회귀 테스트를 실행하고 커밋과 배운 점을 증거 ID에 연결합니다.
5. 다음 학습 때는 `새 학습 시작 · 오늘 기록만 비우기`를 눌러 목표·단계·완료 챕터를 유지한 채 오늘 기록만 초기화합니다.

## Orca에서 고정 URI로 열기

macOS의 Orca 앱에서 아래 명령을 저장소 루트에서 실행합니다.

```bash
./scripts/open_workbook_in_orca.sh
```

문제집은 항상 폴더 이름이 포함된 `http://127.0.0.1:4174/company-work-system/`로 열립니다. 실행 스크립트는 Orca 번들의 공식 CLI를 사용하며, 서버가 없으면 Orca 관리 터미널에서 시작하고 이미 정상 실행 중이면 같은 서버를 재사용한 뒤 새 브라우저 탭을 엽니다. 컴퓨터나 Orca를 다시 시작한 뒤에도 같은 명령을 실행하면 동일한 URI가 복원됩니다.

`4174` 포트를 다른 프로세스가 사용 중이면 해당 프로세스를 임의로 종료하지 않고 오류를 출력합니다. 이 경우 점유 프로세스를 확인해 충돌을 해소한 뒤 같은 명령을 다시 실행합니다. 로컬 서버는 `127.0.0.1`에만 연결되고 워크북 문서와 `practice/` 학습 파일만 제공하며, `.git`, `scripts`, 상위 경로와 디렉터리 목록은 공개하지 않습니다.

## 워크북 화면 검증

HTML 목차나 학습 링크를 바꾼 뒤에는 저장소 루트에서 아래 명령을 실행합니다.

```bash
python3 scripts/verify_workbook.py
```

이 검사는 `index.html`과 `history.html`의 태그·중복 ID·로컬 링크, Markdown 상대 링크, JavaScript 구문과 DOM 연결, 6단계 목차·5단계 로드맵·40개 챕터·이전·다음 탐색·반응형 분기를 한 번에 확인합니다. 또한 Starter 40개와 Hard 33개 프로그램 폴더의 번호·대응 관계, 학습 파일 77개의 빈 파일·내부 목표 또는 챕터 계약·HTML 전수 연결, 챕터별 취업 결과물·완료 검증과 답안·힌트·정답 기준 저장 계약, Orca 고정 URI 서버와 실행 명령도 검사합니다. Python 3와 Node.js가 필요하며, 실패 메시지의 파일·링크·계약을 수정한 뒤 같은 명령이 통과할 때까지 다시 실행합니다.

## 증거 ID 규칙

워크북의 빈칸과 완료 체크는 아래 ID에 실제 링크가 연결될 때만 취업 증거로 인정합니다.

| 종류 | 형식 | 예시 |
|---|---|---|
| 기능 | `E-{FR ID}` | `E-FR-LEAVE-005` |
| 문서·데모 | `E-DOC-{이름}` | `E-DOC-README`, `E-DOC-DEMO` |
| 트러블슈팅 | `E-TS-{번호}` | `E-TS-001` |
| 면접 답변 | `E-INT-{번호}` | `E-INT-001` |

각 증거에는 코드 또는 문서 위치, 검증 명령과 결과, 커밋·PR, 설명할 핵심 선택, 마지막 확인일을 함께 기록합니다.

## 기능 완료 기준

다음 항목을 모두 충족해야 기능 하나를 완료한 것으로 봅니다.

- [ ] 요구사항과 실패 조건을 본인 말로 설명했다.
- [ ] 실행 가능한 프로젝트에 직접 구현했다.
- [ ] 성공, 실패, 권한 또는 상태 전이 테스트를 작성했다.
- [ ] 테스트나 빌드 명령이 통과했다.
- [ ] 한 가지 의도로 설명 가능한 커밋을 남겼다.
- [ ] 설계 선택 또는 문제 해결 내용을 한 문단으로 기록했다.

빈칸의 답을 맞히거나 예제 코드를 읽은 것만으로는 완료가 아닙니다.

## 문서 유지 원칙

- 워크북 기능을 추가하거나 학습 흐름을 바꾸면 관련 안내 문서와 `history.html`을 함께 갱신합니다.
- 예시 코드와 PRD/TRD가 충돌하면 PRD/TRD를 기준으로 차이를 정리합니다.
- 구현하지 않은 기능은 완료된 포트폴리오 기능처럼 표현하지 않습니다.
- 테스트나 빌드를 실행하지 못했다면 그 이유를 결과 기록에 남깁니다.
