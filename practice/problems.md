## 0. 빌드와 애플리케이션 설정 (TRD 3.1, 3.2)

**처음 배우는 개념 · Java·Gradle·Spring Boot**

- **어떤 기술인가요?** Java는 업무 규칙을 작성하는 언어, Gradle은 필요한 라이브러리와 빌드 작업을 관리하는 도구, Spring Boot는 서버 설정을 돕는 틀입니다.
- **왜 쓰나요?** 매번 웹 서버와 DB 연결 도구를 따로 조립하는 수고를 줄입니다.
- **어떻게 동작하나요?** Gradle이 의존성을 준비하고, 실행 시 Spring Boot가 application.yml의 설정을 읽습니다. H2는 연습 데이터를 담고 JPA는 객체와 DB를 연결합니다.

파일:
- `starter/00-build-config/build.gradle.fragment`
- `starter/00-build-config/application.yml.fragment`

**4지선다 문제**

### Q00-01. Spring Boot 의존성과 역할을 올바르게 연결한 것은?

- ① Web가 DB 엔진이고 H2가 HTML 템플릿 엔진이다.
- ② Validation이 Repository 구현을 만들고 JPA가 입력 형식만 검사한다.
- ③ Thymeleaf가 비밀번호 해시를 만들고 H2가 HTTP 요청을 라우팅한다.
- ④ Web는 HTTP·MVC, Data JPA는 영속성, Validation은 입력 검증, Thymeleaf는 템플릿, H2는 DB를 담당한다.

**정답:** ④

**해설:** 각 의존성의 책임을 구분해야 필요한 기능을 빠뜨리거나 불필요한 기능을 활성화하지 않는다.

### Q00-02. 1차 세션 인증에서 BCrypt만 사용할 때 필요한 최소 보안 의존성은?

- ① BCrypt를 사용하려면 모든 요청에 JWT 필터가 필요하다.
- ② H2만 추가하면 PasswordEncoder가 제공된다.
- ③ spring-security-crypto를 사용하고 전체 Security 설정은 2차 확장에서 적용한다.
- ④ spring-boot-starter-security를 넣어도 요청 보안 동작은 전혀 달라지지 않는다.

**정답:** ③

**해설:** crypto는 인코더를 제공한다. 전체 Security starter를 추가하면 인증·인가 자동설정도 고려해야 한다.

### Q00-03. Java 17과 Spring Boot 3.x 예제의 검증 패키지로 알맞은 것은?

- ① javax.validation.constraints를 새 예제의 기본 패키지로 사용한다.
- ② jakarta.validation.constraints
- ③ java.sql.constraints
- ④ org.gradle.validation

**정답:** ②

**해설:** 이 실습의 Spring Boot 3.x 조합은 Jakarta 패키지를 사용한다.

### Q00-04. 운영 DB 스키마를 변경하지 않고 매핑과 일치하는지 검사하는 ddl-auto 값은?

- ① validate
- ② create
- ③ create-drop
- ④ update

**정답:** ①

**해설:** validate는 스키마를 검사하며 생성·변경하지 않는다. 운영 변경은 별도의 마이그레이션 절차로 관리한다.

### Q00-05. 로컬 학습에서 H2 콘솔을 활성화하는 설정은?

- ① spring.jpa.show-sql: true만 설정한다.
- ② server.port: 8080만 설정한다.
- ③ 운영을 포함한 모든 환경에 콘솔을 공개한다.
- ④ spring.h2.console.enabled: true를 로컬 설정에 둔다.

**정답:** ④

**해설:** H2 콘솔 활성화와 SQL 출력은 다른 설정이며 콘솔 공개 범위는 로컬 학습으로 제한한다.

### Q00-06. ddl-auto 옵션과 운영 환경의 선택을 올바르게 설명한 것은?

- ① create는 기존 자료를 항상 보존하므로 운영에서 무조건 사용한다.
- ② validate가 누락된 테이블과 컬럼을 자동으로 생성한다.
- ③ create는 재생성, create-drop은 종료 시 삭제도 수행하고 update는 변경, validate는 검사, none은 자동 처리를 하지 않는다.
- ④ none을 지정하면 모든 SQL 실행이 금지된다.

**정답:** ③

**해설:** 스키마 생성·변경·검사를 구분한다. 운영에서는 validate 또는 none과 별도 마이그레이션을 검토한다.

### Q00-07. show-sql과 Hibernate SQL 로깅 설정을 비교한 설명으로 알맞은 것은?

- ① show-sql을 끄면 DB 쿼리도 실행되지 않는다.
- ② show-sql은 콘솔 출력이고 로깅 설정은 로그 레벨·출력 대상을 관리하며 운영에서는 노출·출력량을 제한한다.
- ③ debug 로깅을 켜면 비밀번호가 자동으로 마스킹된다.
- ④ 두 설정은 테이블 생성 전략을 바꾸는 같은 옵션이다.

**정답:** ②

**해설:** SQL 표시와 실행은 별개다. 로깅 프레임워크로 출력 정책을 관리하고 민감 데이터와 과도한 출력을 점검한다.

### Q00-08. DB 비밀번호와 세션 설정을 외부화하는 올바른 방법은?

- ① 비밀은 환경변수나 비밀 저장소로 주입하고 세션 시간 같은 일반 설정에는 환경별 값과 기본값을 적용한다.
- ② DB 비밀번호를 공개 저장소의 application.yml에 직접 적는다.
- ③ 비밀번호를 주석으로 옮기면 안전하다.
- ④ 세션 시간에 기본값을 두면 비밀번호 암호화까지 자동 적용된다.

**정답:** ①

**해설:** 외부화는 환경별 설정과 비밀 관리에 도움이 된다. 비밀에 공개된 기본 비밀번호를 두는 방식은 피한다.

### Q00-09. Spring Boot starter가 단일 라이브러리와 다른 점은?

- ① 모든 starter는 단 하나의 jar만 제공한다.
- ② starter는 애플리케이션의 업무 코드를 자동으로 완성한다.
- ③ starter-web을 추가하면 모든 DB 엔티티가 자동 생성된다.
- ④ 목적에 맞는 관련 의존성을 묶어 제공하고 Boot 자동 설정과 함께 필요한 구성을 줄인다.

**정답:** ④

**해설:** starter는 관련 라이브러리 묶음이다. 자동 설정은 classpath와 설정 조건에 따라 동작한다.

### Q00-10. dependency-management와 BOM을 사용하는 이유로 알맞은 것은?

- ① 어떤 라이브러리든 버전과 호환성을 확인할 필요가 없어진다.
- ② BOM은 Java 소스의 문법 오류를 수정한다.
- ③ 관리 대상 버전을 모두 임의로 바꿔야 호환성이 보장된다.
- ④ BOM이 관리하는 호환 버전 조합을 적용해 관리 대상 의존성의 버전 선언을 줄인다.

**정답:** ④

**해설:** Spring Boot BOM이 관리하는 버전을 기본으로 사용하고 관리 밖 의존성과 개별 버전 재정의는 따로 검토한다.

### Q00-11. Boot 3.x로 옮길 때 JPA·Validation 코드에서 확인할 변경은?

- ① 관련 import와 의존성을 jakarta.persistence·jakarta.validation 기반으로 맞춘다.
- ② java.time을 모두 javax.time으로 바꾼다.
- ③ 모든 javax 패키지를 이름만 보고 무조건 jakarta로 치환한다.
- ④ JPA 어노테이션을 모두 삭제하면 자동으로 호환된다.

**정답:** ①

**해설:** Jakarta 전환 대상 API와 라이브러리를 함께 맞춘다. javax라는 이름의 모든 Java API가 전환 대상인 것은 아니다.

### Q00-12. 세션 실습에서 crypto와 전체 Security starter를 단계별로 도입하는 이유는?

- ① crypto만으로 모든 URL의 접근 권한이 자동 검사된다.
- ② 먼저 BCrypt 인코더를 쓰고 이후 전체 인증·인가 필터와 보안 설정을 함께 적용하기 위해서다.
- ③ Security starter는 비밀번호를 평문으로 저장하기 위해 필요하다.
- ④ 두 의존성은 HTTP 요청 동작에 언제나 동일한 영향을 준다.

**정답:** ②

**해설:** 인코더 사용과 요청 보안 적용의 범위가 다르므로 전체 Security를 넣을 때 필터와 접근 정책도 구성한다.

## 1. User 엔티티 (TRD 3.3.1, 3.6.1)

**처음 배우는 개념 · Entity와 enum**

- **어떤 기술인가요?** Entity는 DB에 저장할 대상을 표현하는 Java 객체이고, enum은 허용할 값을 이름으로 정한 타입입니다.
- **왜 쓰나요?** 로그인 계정의 저장 구조와 USER·MANAGER·ADMIN 같은 역할을 일관되게 표현합니다.
- **어떻게 동작하나요?** User.create가 계정을 만들고 JPA 매핑이 users 테이블의 컬럼과 필드를 연결합니다. 비밀번호 필드에는 별도 인코더로 만든 해시를 전달합니다.

파일: `starter/01-user-entity/User.entity.java`

**4지선다 문제**

### Q01-01. User를 JPA 엔티티로 선언하고 기본 키 생성을 지정한 조합은?

- ① @RestController, @RequestBody, @Valid, @GetMapping
- ② @Service, @Transactional, @Bean, @Configuration
- ③ @Entity, @Table, @Id, @GeneratedValue
- ④ @NotBlank, @Email, @Size, @Pattern

**정답:** ③

**해설:** Entity·Table은 저장 대상을, Id·GeneratedValue는 기본 키와 생성 전략을 지정한다.

### Q01-02. 로그인 계정의 이메일과 비밀번호 저장 정책으로 알맞은 것은?

- ① 이메일과 평문 비밀번호를 모두 unique로 저장한다.
- ② 비밀번호를 Base64로 바꾸면 해시와 동일한 보호가 된다.
- ③ 이메일 중복은 화면 검사만으로 보장한다.
- ④ 이메일 중복은 DB unique로 보장하고 비밀번호는 해시 결과를 저장한다.

**정답:** ④

**해설:** 중복 무결성은 DB 제약으로 보장하며 비밀번호 검증은 원문 저장 없이 해시 비교로 수행한다.

### Q01-03. UserRole을 EnumType.STRING으로 저장하는 주된 이유는?

- ① enum 선언 순서가 바뀌어도 기존 저장값의 의미가 유지된다.
- ② enum 이름을 바꿔도 DB 마이그레이션이 항상 필요 없다.
- ③ 모든 역할에 자동으로 관리자 권한을 부여한다.
- ④ enum을 DB에 저장하지 않도록 한다.

**정답:** ①

**해설:** STRING은 이름을 저장하므로 순서 변경에 안전하다. 이름을 변경하는 경우에는 기존 데이터 이관을 검토한다.

### Q01-04. JPA Auditing으로 생성·수정 시각을 채우려면 필요한 구성은?

- ① @CreatedDate만 붙이면 모든 설정과 리스너가 생략된다.
- ② 시간 필드 어노테이션과 AuditingEntityListener, @EnableJpaAuditing을 연결한다.
- ③ Controller에서 응답 직전에만 시각을 바꾼다.
- ④ 매 조회마다 createdAt을 현재 시각으로 덮어쓴다.

**정답:** ②

**해설:** Auditing 필드와 리스너, 기능 활성화가 함께 있어야 저장 시각을 기록할 수 있다.

### Q01-05. 로그인 계정과 인사 정보를 분리하는 설계의 이점은?

- ① 계정과 직원의 관계를 검증하지 않아도 된다.
- ② 모든 직원이 같은 비밀번호를 공유하게 한다.
- ③ 인증·권한과 인사 정보의 책임·변경 주기를 나누고 명시적인 관계로 연결한다.
- ④ 테이블이 둘이면 개인정보 노출이 자동으로 불가능해진다.

**정답:** ③

**해설:** User는 인증 정보를, Employee는 인사 정보를 맡는다. 분리 뒤에도 관계 무결성과 공개 필드 정책을 검증한다.

### Q01-06. enum을 ORDINAL로 저장한 뒤 선언 순서를 바꾸면 생길 수 있는 문제는?

- ① 숫자 저장값이 항상 이름으로 자동 이관된다.
- ② ORDINAL이 모든 순서 변경을 거부한다.
- ③ 역할을 재정렬하면 사용자 행이 모두 자동 삭제된다.
- ④ 기존 숫자가 다른 enum 상수를 가리켜 역할의 의미가 바뀔 수 있다.

**정답:** ④

**해설:** ORDINAL은 순서에 의존한다. STRING은 순서 변경에 안전하지만 상수 이름 변경에는 데이터 이관을 검토한다.

### Q01-07. 비밀번호 해시 컬럼 길이를 255로 잡는 판단으로 알맞은 것은?

- ① BCrypt 결과를 수용하고 인코더 식별자·향후 해시 형식 변경도 고려한 여유를 둔다.
- ② BCrypt 결과는 반드시 255자여야 한다.
- ③ 해시 컬럼이 길수록 BCrypt 계산 강도가 자동 증가한다.
- ④ 255자 컬럼이면 평문 비밀번호 저장도 안전하다.

**정답:** ①

**해설:** 일반적인 BCrypt 문자열은 60자이므로 100자도 수용한다. 255자는 저장 형식의 확장을 고려한 선택이며 필수 BCrypt 길이는 아니다.

### Q01-08. createdAt의 updatable=false와 JPA Auditing 설정의 역할은?

- ① updatable=false 하나만으로 현재 시각을 생성한다.
- ② 생성 시각의 일반 UPDATE 반영을 막고 리스너·활성화 설정으로 생성 시각을 채운다.
- ③ @CreatedDate를 붙이면 리스너와 활성화 설정은 항상 필요 없다.
- ④ createdAt은 조회마다 현재 시각으로 덮어써야 한다.

**정답:** ②

**해설:** updatable=false는 갱신 매핑 설정이고 Auditing은 값 입력 기능이다. 필드·리스너·@EnableJpaAuditing을 연결한다.

## 2. Department 엔티티 (TRD 3.3.3, 3.5.2)

**처음 배우는 개념 · 테이블 제약과 관계**

- **어떤 기술인가요?** unique 제약은 같은 값의 중복 저장을 DB에서 막는 규칙입니다.
- **왜 쓰나요?** 동일한 부서가 중복 생성되어 직원 정보가 나뉘는 일을 방지합니다.
- **어떻게 동작하나요?** 부서 이름과 설명을 객체에 담고 저장합니다. 직원은 부서 ID를 참조합니다. 객체의 양방향 관계를 추가할지는 실제 조회 요구에 따라 결정합니다.

파일: `starter/02-department-entity/Department.entity.java`

**4지선다 문제**

### Q02-01. 부서명에 DB unique 제약을 두는 이유는?

- ① 부서명으로 로그인 인증을 하기 위해서다.
- ② 동시 등록에서도 동일한 부서명의 중복 저장을 막기 위해서다.
- ③ 직원 조회의 모든 N+1 쿼리를 없애기 위해서다.
- ④ 부서 설명을 자동으로 암호화하기 위해서다.

**정답:** ②

**해설:** Service의 사전 검사만으로는 동시 요청을 막지 못하므로 DB 제약이 최종 방어선이다.

### Q02-02. 부서에서 직원으로의 탐색이 필수가 아닐 때 단방향 관계의 장점은?

- ① Employee에서 Department를 참조하고 직원 목록은 쿼리로 조회하여 양방향 동기화 부담을 줄인다.
- ② 단방향이면 부서 외래키 제약을 설정할 수 없다.
- ③ 양방향 매핑은 언제나 SQL을 한 번만 실행한다.
- ④ 양방향으로 바꾸면 JSON 순환 참조가 자동으로 사라진다.

**정답:** ①

**해설:** 양방향은 탐색 편의와 함께 양쪽 관계 관리·직렬화 부담을 가져오므로 요구에 따라 선택한다.

### Q02-03. 부서명 100자와 설명 255자 제한을 설계할 때 알맞은 판단은?

- ① DB 길이는 UI 글자 색상으로 정한다.
- ② 모든 문자열을 한 글자로 제한하면 업무 요구를 만족한다.
- ③ DB 길이는 숫자 ID의 생성 순서를 뜻한다.
- ④ 필드의 업무 의미와 허용 길이를 정하고 DTO와 DB 제약을 일치시킨다.

**정답:** ④

**해설:** 문자열 길이는 입력 계약과 저장 구조가 일치하도록 업무 요구를 기준으로 정한다.

### Q02-04. 사전 중복 검사 뒤에도 부서명 unique가 필요한 동시성 이유는?

- ① existsByName은 모든 다른 트랜잭션을 자동 잠근다.
- ② unique가 있으면 모든 입력 검증을 생략해야 한다.
- ③ 두 요청이 동시에 사전 검사를 통과해도 DB가 최종 중복 저장을 막아야 하기 때문이다.
- ④ 중복 검사는 화면에서만 해야 한다.

**정답:** ③

**해설:** 사전 조회와 INSERT 사이에 다른 요청이 들어올 수 있다. DB 제약과 충돌 오류 응답을 함께 다룬다.

### Q02-05. 부서명 trim 처리를 도메인 팩토리에 두는 이점은?

- ① trim이 대소문자와 모든 유니코드 표기를 자동 통일한다.
- ② 다른 생성 경로에서도 공백 정규화 규칙을 일관되게 적용한다.
- ③ Service에서 생성할 때만 공백이 제거된다.
- ④ trim은 DB unique 제약을 대신한다.

**정답:** ②

**해설:** 생성 규칙을 팩토리에 모으면 누락을 줄인다. 필요한 추가 정규화와 DB 제약은 별도로 설계한다.

### Q02-06. 부서 수정에서 제공된 필드만 바꾸려는 의도를 나타내는 HTTP 메서드는?

- ① 부분 변경 계약의 PATCH를 사용한다.
- ② 자원 읽기 계약의 GET을 사용한다.
- ③ 자원 삭제 계약의 DELETE를 사용한다.
- ④ 폼 입력에 빈 값이 있으면 PUT도 항상 부분 변경을 뜻한다.

**정답:** ①

**해설:** PATCH는 부분 변경을 위한 메서드다. 생략·null·공백의 처리 의미도 요청 계약에 명시한다.

### Q02-07. 부서명 수정의 중복 검사에서 자기 자신을 제외하는 이유는?

- ① 현재 부서와 다른 부서 모두의 중복 검사를 없애기 위해서다.
- ② 부서 ID가 같으면 DB 제약을 삭제하기 위해서다.
- ③ 부서명을 변경할 때마다 새 부서를 만들기 위해서다.
- ④ 현재 부서의 기존 이름을 유지하는 요청을 다른 부서와의 중복으로 오판하지 않기 위해서다.

**정답:** ④

**해설:** 이름이 같은 다른 ID의 부서가 있는지 검사한다. 본인의 행은 중복 대상에서 제외하되 DB unique는 유지한다.

## 3. Employee 엔티티 (TRD 3.3.2, 3.5.3, 3.6.2)

**처음 배우는 개념 · JPA 연관관계와 지연 로딩**

- **어떤 기술인가요?** 연관관계는 직원과 계정·부서를 연결하며, LAZY는 관련 객체의 조회를 필요할 때까지 미루는 설정입니다.
- **왜 쓰나요?** 한 부서에 여러 직원이 속한다는 구조를 표현하고 불필요한 관련 데이터 조회를 줄입니다.
- **어떻게 동작하나요?** Employee의 user_id와 department_id가 다른 테이블을 참조합니다. 관련 객체를 읽을 때 추가 SQL이 나갈 수 있으므로 LAZY만으로 N+1 문제가 해결되지는 않습니다.

파일: `starter/03-employee-entity/Employee.entity.java`

**4지선다 문제**

### Q03-01. Employee의 User·Department 관계로 알맞은 것은?

- ① Employee–User는 1:1, 여러 Employee–한 Department는 N:1이다.
- ② Employee–User는 N:1이고 Employee–Department는 항상 1:1이다.
- ③ 모든 직원은 모든 계정을 동시에 공유한다.
- ④ 직원과 부서는 관계 없이 같은 ID 숫자만 쓰면 연결된다.

**정답:** ①

**해설:** 계정과 직원의 1:1 연결, 부서와 직원의 1:N 구조를 외래키로 표현한다.

### Q03-02. JPA 관계에서 LAZY를 선택할 때 올바른 설명은?

- ① LAZY를 지정하면 관계 접근 시 SQL이 절대로 실행되지 않는다.
- ② 관계 조회를 필요할 때까지 미루며 N+1은 별도의 조회 설계로 해결한다.
- ③ LAZY는 트랜잭션 없이도 모든 관계를 항상 읽게 한다.
- ④ LAZY 하나만으로 모든 N+1 문제가 해결된다.

**정답:** ②

**해설:** 지연 로딩은 조회 시점을 바꾸는 기능이다. 쿼리 수와 접근 시점은 fetch join·DTO 조회 등으로 검증한다.

### Q03-03. 이 실습에서 사용하는 직원 상태 enum의 조합은?

- ① DRAFT, PENDING, APPROVED
- ② USER, APPROVER, ADMIN
- ③ ACTIVE, INACTIVE, RESIGNED
- ④ GET, POST, PATCH

**정답:** ③

**해설:** 직원의 재직 상태와 문서 처리 상태·사용자 역할은 서로 다른 개념이다.

### Q03-04. 퇴사 직원의 행을 삭제하는 대신 RESIGNED로 남기는 이유는?

- ① 퇴사한 직원에게 새 휴가 신청을 계속 허용하기 위해서다.
- ② 모든 직원의 비밀번호를 함께 초기화하기 위해서다.
- ③ 직원 ID를 다른 직원에게 즉시 재사용하기 위해서다.
- ④ 과거 휴가·결재의 참조와 인사 이력을 보존하기 위해서다.

**정답:** ④

**해설:** 업무 이력 보존과 신규 업무 수행 제한을 함께 적용하는 상태 처리다.

### Q03-05. 직원 관계를 EAGER 대신 LAZY로 설정할 때 함께 해야 할 일은?

- ① 불필요한 즉시 조회를 줄이고 실제 목록 쿼리 수를 확인해 fetch join·DTO 조회 등으로 N+1을 조정한다.
- ② LAZY 하나면 모든 N+1 문제가 사라진다고 가정한다.
- ③ EAGER는 언제나 한 개의 조인 SQL만 실행한다고 가정한다.
- ④ LAZY 객체는 트랜잭션 없이 언제나 로딩된다고 가정한다.

**정답:** ①

**해설:** fetch 전략만으로 쿼리 수를 보장할 수 없다. 접근 경로와 실제 SQL을 함께 검증한다.

### Q03-06. 퇴사를 RESIGNED 상태로 남기는 주된 업무 이유는?

- ① 퇴사자의 신규 휴가를 무제한 허용하기 위해서다.
- ② 과거 휴가·결재의 참조와 인사 이력을 보존하면서 신규 업무 허용 여부를 제한하기 위해서다.
- ③ 퇴사자의 계정 ID를 즉시 다른 사람에게 넘기기 위해서다.
- ④ 비밀번호를 자동 공개하기 위해서다.

**정답:** ②

**해설:** 이력 보존과 활성 사용자 정책을 함께 적용한다. 상태만 바꾸고 접근 제한을 빠뜨리지 않는다.

### Q03-07. setter 대신 resign·changeDepartment 같은 메서드를 두는 이점은?

- ① 필드를 언제나 검증 없이 바꾸게 한다.
- ② Service의 권한 검사와 트랜잭션을 전부 없앤다.
- ③ 변경의 업무 의도와 검사 규칙을 한곳에 모아 불변식 우회를 줄인다.
- ④ 메서드 이름만 바꾸면 동시성 제어도 자동 적용된다.

**정답:** ③

**해설:** 도메인 변경 메서드는 상태·입력 규칙을 지킨다. 인증·권한과 외부 작업 조정은 별도 책임이다.

### Q03-08. isActive 판단을 Entity 메서드로 모으는 이유는?

- ① Entity가 모든 HTTP 인증을 대신 처리하기 위해서다.
- ② 상태 필드 자체를 제거하기 위해서다.
- ③ isActive를 호출하면 상태가 항상 ACTIVE로 바뀌기 때문이다.
- ④ 활성 상태의 정의를 재사용하고 Service마다 다른 조건이 생기는 것을 줄이기 위해서다.

**정답:** ④

**해설:** 상태를 판단하는 규칙을 데이터 옆에 둔다. 판단 메서드와 상태 변경 메서드는 구분한다.

## 4. LeaveRequest 엔티티와 enum (TRD 3.3.4, 3.6.3, 3.6.4)

**처음 배우는 개념 · LocalDate와 상태 모델**

- **어떤 기술인가요?** LocalDate는 시각 없는 날짜를, 상태 enum은 신청의 처리 단계를 표현합니다.
- **왜 쓰나요?** 휴가 기간과 승인 여부를 자유로운 문자열 대신 정해진 규칙으로 다룹니다.
- **어떻게 동작하나요?** create에서 날짜와 초기 상태를 정하고 approve·reject 같은 메서드가 허용된 상태인지 확인한 뒤 승인자와 처리 결과를 변경합니다.

파일: `starter/04-leave-entity/LeaveRequest.entity.java`

**4지선다 문제**

### Q04-01. 휴가 시작일과 종료일에 LocalDate를 사용하는 이유는?

- ① 초 단위 승인 시각을 저장하기 위해서다.
- ② 브라우저 세션 ID를 저장하기 위해서다.
- ③ 시각과 시간대 없이 업무상의 날짜를 표현하기 위해서다.
- ④ 날짜 비교를 하지 못하도록 하기 위해서다.

**정답:** ③

**해설:** 휴가 기간의 날짜와 승인 순간의 시각은 목적이 다르므로 자료형을 구분한다.

### Q04-02. 휴가 신청 생성 시 초기 상태를 두는 위치와 값은?

- ① 응답 DTO에서만 APPROVED로 표시한다.
- ② 신청자가 임의의 완료 상태를 보내면 그대로 저장한다.
- ③ 조회할 때마다 REJECTED로 초기화한다.
- ④ 생성 팩토리에서 PENDING으로 설정한다.

**정답:** ④

**해설:** 새 신청의 시작 상태를 도메인 생성 규칙에 두면 호출 경로와 관계없이 유지된다.

### Q04-03. 휴가 승인·반려 결과를 올바르게 기록한 것은?

- ① 승인 시 처리자 ID를 기록하고 반려 시 처리자와 사유를 규칙에 따라 기록한다.
- ② 승인 시 신청자 ID를 처리자 ID로 무조건 복사한다.
- ③ 반려 사유는 화면에만 보이고 서버에는 저장하지 않는다.
- ④ 반려 시 휴가 기간을 삭제하여 사유를 대신한다.

**정답:** ①

**해설:** 처리 행위자와 반려 이유는 감사와 상태 설명에 필요한 별도 정보다.

### Q04-04. 신청자와 승인자를 별도 필드로 표현하는 이유는?

- ① 승인 시 신청자를 자동으로 다른 사람으로 바꾸기 위해서다.
- ② 신청한 직원과 처리한 직원이 서로 다른 업무 역할이기 때문이다.
- ③ 처리자의 인증을 생략하기 위해서다.
- ④ 같은 필드를 두 이름으로 저장하여 혼동시키기 위해서다.

**정답:** ②

**해설:** 신청 소유권과 승인 권한을 서로 다른 식별자로 검증한다.

### Q04-05. 휴가 상태 검사를 Service에만 두었을 때의 우회 위험은?

- ① 모든 Entity 호출이 자동으로 Service를 거친다.
- ② DB가 모든 자바 상태 전이를 자동 검사한다.
- ③ 다른 호출 경로가 Entity를 직접 변경하면 완료된 휴가를 다시 승인할 수 있다.
- ④ Controller에 버튼이 없으면 재승인 호출도 불가능하다.

**정답:** ③

**해설:** approve·reject 내부에서 허용 상태를 확인해야 호출 경로가 달라도 도메인 규칙을 지킨다.

### Q04-06. 휴가와 결재가 상태 enum을 공유할 때 올바른 설계는?

- ① enum에 DRAFT가 있으므로 모든 휴가를 DRAFT로 만든다.
- ② 같은 enum을 쓰면 두 업무의 상태 전이가 항상 같다.
- ③ 요청에서 어떤 enum 값이 오든 저장한다.
- ④ 공통 이름을 재사용하되 휴가에 허용되지 않는 DRAFT 상태를 생성·전이 규칙으로 막는다.

**정답:** ④

**해설:** 상태 이름 공유와 업무별 허용 상태는 별개다. 필요하면 별도 enum으로 더 강하게 제약할 수 있다.

### Q04-07. 두 관리자의 동시 휴가 승인에서 상태 검사만으로 부족한 이유는?

- ① 둘 다 PENDING을 읽을 수 있으므로 낙관적 버전 검사나 비관적 잠금과 충돌 처리가 필요하다.
- ② PENDING 문자열이 자동으로 DB 잠금을 건다.
- ③ @Transactional만 붙이면 모든 동시 승인이 순서대로 실행된다.
- ④ 나중 요청의 결과를 무조건 덮어쓰면 승인 이력도 안전하다.

**정답:** ①

**해설:** 읽은 뒤 쓰기까지의 경쟁을 제어해야 한다. @Version 충돌 또는 잠금 정책과 재시도·실패 응답을 검증한다.

### Q04-08. 휴가 취소를 반려와 구분하는 상태의 이점은?

- ① 취소한 휴가를 승인 통계에 반드시 더한다.
- ② 신청자의 취소와 관리자의 반려를 구별해 통계·이력의 의미를 보존한다.

- ③ @Query로 옮기면 쿼리 검증이 필요 없어지는지 확인한다.
- ④ Repository 없이 Controller에서 문자열 SQL만 연결한다.

### Q07-08. Page<Employee>를 API 응답에 직접 노출하는 대신 해야 할 일은?

**정답:** ②

**해설:** 페이지 메타정보는 유지하면서 Entity의 공개 범위·지연 로딩·API 계약을 DTO로 관리한다.

### Q08-07. 이메일 사전 중복 검사와 DB unique의 역할을 올바르게 연결한 것은?

- ① 사전 검사만으로 동시 요청도 완전히 직렬화된다.

### Q10-06. 휴가 신청 저장 후 외부 알림을 보내는 안전한 기본 흐름은?

## 15. ErrorCode 와 응답 모델 (TRD 3.9)

**처음 배우는 개념 · 예외와 오류 응답 모델**

- **어떤 기술인가요?** 예외는 정상 처리를 계속할 수 없다는 신호이고 ErrorCode는 실패 이유의 공통 이름입니다.
- **왜 쓰나요?** 각 기능이 서로 다른 형식의 오류를 보내면 화면과 테스트에서 처리하기 어렵습니다.
- **어떻게 동작하나요?** 업무 코드가 BusinessException에 오류 코드를 담아 던집니다. ErrorResponse는 클라이언트에 보낼 코드·메시지 등을 담으며 HTTP 응답 변환은 다음 장의 처리기가 맡습니다.

파일: `starter/15-error-model/ErrorCodeAndResponse.java`

**4지선다 문제**

### Q15-01. HTTP status와 업무 오류 코드의 관계로 알맞은 것은?

- ① 업무 오류 코드는 항상 HTTP status와 같은 숫자여야 한다.
- ② 실패를 모두 HTTP 200으로 숨기면 코드가 필요 없다.
- ③ HTTP status는 응답 범주, 업무 코드는 구체적인 실패 원인을 표현한다.
- ④ HTTP status는 DB 테이블 이름을 지정한다.

**정답:** ③

**해설:** 동일한 HTTP 400이라도 날짜 오류와 중복 오류 등 업무 원인은 코드로 구분할 수 있다.

### Q15-02. 공통 ErrorResponse가 가져야 할 기본 정보는?

- ① 평문 비밀번호, 세션 쿠키, DB 비밀번호, 전체 스택 추적
- ② createdAt 한 필드만 필요하다.
- ③ 공지 제목, 조회수, important, 부서명
- ④ status, code, message, timestamp

**정답:** ④

**해설:** 오류 계약에 필요한 정보만 공개하고 내부 비밀과 상세 스택을 응답에 노출하지 않는다.

### Q15-03. ErrorCode enum을 도메인별로 관리하는 장점은?

- ① 실패 원인과 응답 메시지를 일관된 계약으로 관리한다.
- ② 모든 예외를 제거하고 저장을 항상 성공시키는 것이다.
- ③ ErrorCode가 있으면 인증·인가 검사를 생략할 수 있다.
- ④ DB 무결성 제약을 더 이상 두지 않아도 된다.

**정답:** ①

**해설:** 표준 오류 코드는 의미와 HTTP 매핑을 일관되게 제공하지만 실제 검증을 대신하지 않는다.

### Q15-04. ErrorResponse에서 HTTP status와 업무 code를 분리하는 이유는?

- ① 모든 업무 오류를 HTTP 200으로 숨기기 위해서다.
- ② 전송 수준 결과와 구체적인 업무 실패 원인을 각각 안정적으로 표현하기 위해서다.
- ③ 업무 code가 있으면 HTTP 상태는 전혀 필요 없기 때문이다.
- ④ HTTP status에 사용자의 비밀번호를 넣기 위해서다.

**정답:** ②

**해설:** 같은 HTTP 상태 안에 여러 업무 원인이 있을 수 있다. 상태·코드·메시지의 계약을 분리한다.

### Q15-05. 클라이언트 ErrorResponse에 stack trace를 넣지 않는 이유는?

- ① stack trace를 숨기면 서버 로그도 반드시 삭제해야 하기 때문이다.
- ② stack trace가 없으면 모든 오류가 자동 복구되기 때문이다.
- ③ 내부 구조·경로 등 정보 노출을 줄이고 상세 원인은 서버 로그와 추적 ID로 관리하기 위해서다.
- ④ 클라이언트가 DB 비밀번호를 알아야 복구할 수 있기 때문이다.

**정답:** ③

**해설:** 공개 오류 계약과 내부 진단 정보를 분리한다. 로그에도 민감 정보를 과도하게 기록하지 않는다.

### Q15-06. BusinessException을 Checked Exception으로 바꿀 때 고려할 점은?

- ① Checked Exception도 모든 기본 설정에서 반드시 자동 롤백된다.
- ② Checked Exception은 HTTP 응답에서 사용할 수 없다.
- ③ Checked Exception은 컴파일러가 언제나 무시한다.
- ④ 호출자의 throws·catch 부담과 기본 트랜잭션 롤백 규칙에 맞춘 rollbackFor 설정 등을 검토한다.

**정답:** ④

**해설:** 체크 예외는 처리·선언 요구가 있다. 기본 롤백과 명시적 롤백 설정을 구분하여 실패 저장 테스트를 수행한다.

## 17. DTO 검증 (TRD 3.7, 비기능 검증)

### Q17-01. 요청 DTO 검증 어노테이션의 의미를 올바르게 연결한 것은?

- ③ NotBlank는 공백 금지, Email은 이메일 형식, Size는 크기 범위, Pattern은 정규식이다.
- ④ Size는 날짜 순서를 자동으로 비교하고 Email은 세션을 만든다.

**정답:** ③

**해설:** 형식 제약과 업무·DB 규칙은 다른 책임이다. 필수 이메일은 NotBlank 등도 함께 적용한다.

### Q17-02. Spring MVC 요청 본문 검증에서 @Valid를 적용하는 일반적인 위치는?

- ① HTML 스타일시트의 선택자에 적용한다.
- ② 응답 문자열에만 적용하여 요청 검사를 대신한다.
- ③ DB 포트 번호에 적용한다.
- ④ Controller의 요청 DTO 인자에 적용한다.

**정답:** ④

**해설:** MVC가 바인딩한 요청 DTO를 검증하고 실패를 예외 처리 흐름으로 전달한다.

### Q17-03. 요청 DTO와 응답 DTO를 분리하는 이유는?

- ① 입력 제약과 외부에 공개할 필드가 서로 다르기 때문이다.
- ② 요청 비밀번호를 응답에 되돌려 주기 위해서다.
- ③ 모든 필드를 Entity에 직접 연결해 과도한 변경을 허용하기 위해서다.
- ④ DTO 이름이 다르면 인가가 자동 적용되기 때문이다.

**정답:** ①

**해설:** 요청 허용 범위와 응답 공개 범위를 각각 명확하게 관리한다.

### Q17-04. NotNull·NotEmpty·NotBlank를 올바르게 비교한 것은?

- ① NotNull은 빈 문자열과 공백을 모두 금지한다.
- ② NotNull은 null 금지, NotEmpty는 null·빈 컨테이너 금지, NotBlank는 null·공백뿐인 문자열 금지다.
- ③ NotEmpty는 공백 문자열도 반드시 금지한다.
- ④ NotBlank는 어떤 숫자 자료형에도 문자열처럼 적용한다.

**정답:** ②

**해설:** 제약마다 적용 자료형과 허용 값이 다르다. null·빈 값·공백 입력을 구분해 테스트한다.

### Q17-05. 요청 DTO 제약을 MVC에서 검사하려는 파라미터의 일반적인 구성은?

- ① @RequestBody만 붙이면 모든 제약이 자동 검사된다.
- ② @Entity만 붙이면 요청 DTO가 검증된다.
- ③ @Valid @RequestBody로 DTO를 받고 검증 오류를 공통 응답으로 처리한다.
- ④ @Transactional만 붙이면 문자열 길이가 검사된다.

**정답:** ③

**해설:** 본문 바인딩과 제약 검증은 다른 단계다. 검증 실행 설정과 실패 응답 계약을 함께 확인한다.

### Q17-06. 요청 DTO와 응답 DTO를 분리하는 이유로 알맞은 것은?

- ① 분리하면 모든 필드가 자동으로 암호화된다.
- ② 응답의 민감 정보를 요청에도 모두 허용하기 위해서다.
- ③ 분리하면 API 변경 검토가 필요 없어진다.
- ④ 입력 허용 필드·검증 규칙과 공개 응답 필드가 달라 과입력·정보 노출·계약 결합을 줄이기 위해서다.

**정답:** ④

**해설:** 입력과 출력의 목적별 계약을 설계한다. 특히 비밀번호·역할·서버 관리 값의 입력과 공개 범위를 명시한다.

## 23. 인증 — 로그인 / 로그아웃 / 내 정보 / 비밀번호 변경 (PRD 2.5.1, TRD 3.7.1, 3.11)

**처음 배우는 개념 · BCrypt와 로그인 세션**

- **어떤 기술인가요?** BCrypt는 비밀번호를 단방향 해시로 저장하는 방법이고 세션은 서버가 로그인 상태를 기억하는 공간입니다.
- **왜 쓰나요?** 평문 비밀번호 저장을 피하고 매 요청마다 비밀번호를 다시 보내지 않게 합니다.
- **어떻게 동작하나요?** 가입은 encode, 로그인은 matches로 비교합니다. 성공 후 Controller가 세션 ID를 바꾸고 USER_ID·USER_ROLE을 저장하며 로그아웃은 세션을 폐기합니다.

파일:
- `starter/23-auth-login/AuthService.login.java`
- `starter/23-auth-login/AuthController.java`

**4지선다 문제**

### Q23-01. 로그인 이메일·비밀번호 검증으로 알맞은 것은?

- ① 이메일을 정규화해 계정을 찾고 passwordEncoder.matches로 해시와 비교한다.
- ② 입력 비밀번호를 DB 해시와 문자열 equals로 비교한다.
- ③ 매번 새 BCrypt 해시를 생성해 equals로만 비교한다.
- ④ 이메일이 있으면 비밀번호 없이 로그인시킨다.

**정답:** ①

**해설:** BCrypt는 salt가 있으므로 원문과 저장 해시는 matches로 검증한다.

### Q23-02. 로그인 Service의 책임으로 알맞은 것은?

- ② 계정·비밀번호를 검증하고 로그인 결과 DTO를 반환한다.
- ③ 브라우저 localStorage에 쿠키를 생성한다.
- ④ 요청자가 정한 역할을 검사 없이 반환한다.

**정답:** ②

**해설:** Service는 인증 업무를 처리하고 HTTP 세션 생성은 Controller가 담당한다.

### Q23-03. 로그인 Controller의 세션 처리로 알맞은 것은?

- ② 평문 비밀번호를 세션 쿠키에 저장한다.
- ③ 검증된 로그인 결과의 사용자 ID·역할을 서버 세션에 저장한다.
- ④ 조회한 모든 Entity를 외부 쿠키 문자열로 반환한다.

**정답:** ③

**해설:** 신뢰할 수 있는 인증 결과에서 세션 정보를 만들며 비밀 정보를 불필요하게 보관하지 않는다.

### Q23-04. 로그인 성공 시 세션 ID를 갱신하는 이유는?

- ② JPA 외래키를 바꾸기 위해서다.
- ③ 페이지 정렬 순서를 바꾸기 위해서다.
- ④ 세션 고정 공격을 줄이기 위해 인증 전후 세션 식별자를 바꾼다.

**정답:** ④

**해설:** 이미 알려진 세션 ID가 인증 후에도 그대로 사용되는 위험을 줄인다.

### Q23-05. 로그인 실패를 이메일 오류와 비밀번호 오류로 구분하지 않는 이유는?

- ① 외부에 계정 존재 여부를 쉽게 노출하지 않기 위해서다.
- ② 서버 내부 로그도 절대로 남기면 안 되기 때문이다.
- ③ 모든 실패를 로그인 성공으로 처리하기 위해서다.
- ④ 비밀번호 검증을 생략하기 위해서다.

**정답:** ①

**해설:** 외부 메시지는 일반화하면서 내부 진단은 비밀을 노출하지 않는 방식으로 수행한다.

### Q23-06. 비밀번호 변경의 안전한 처리 순서는?

- ① 새 비밀번호를 원문으로 저장 → 현재 비밀번호 확인
- ② 현재 비밀번호 확인 → 새 비밀번호 검증·해시 → 저장
- ③ 이메일만 알면 누구든 비밀번호를 변경한다.
- ④ 기존 해시를 복호화하여 새 비밀번호로 사용한다.

**정답:** ②

**해설:** 비밀번호 변경 권한을 확인하고 새 원문도 해시 결과만 저장한다.

### Q23-07. Security 적용 단계에서 로그인 경로에 permitAll을 설정하는 이유는?

- ① 로그인 성공 여부와 관계없이 관리자 역할을 주기 위해서다.
- ② permitAll이면 모든 필터와 CSRF 정책이 자동 해제되기 때문이다.
- ③ 아직 인증되지 않은 사용자도 자격 증명으로 로그인할 수 있어야 하기 때문이다.
- ④ 로그인 요청을 DB에 저장하지 못하게 하기 위해서다.

**정답:** ③

**해설:** 로그인 전 접근을 허용하되 자격 증명 검증과 적용 중인 다른 보안 정책은 유지한다.

### Q23-08. 내 비밀번호 변경을 PATCH 계약으로 나타내는 이유는?

- ① 비밀번호 변경은 읽기 전용 GET 요청이기 때문이다.
- ② PATCH는 비밀번호를 평문 저장하도록 강제하기 때문이다.
- ③ PATCH 요청이면 현재 비밀번호·인증 확인을 생략하기 때문이다.
- ④ 현재 사용자 자원의 일부인 비밀번호를 지정된 검증 절차에 따라 변경하기 위해서다.

**정답:** ④

**해설:** 부분 변경 계약과 본인 확인·새 비밀번호 정책·세션 처리 규칙을 함께 설계한다.

### Q23-09. 로그인 응답의 사용자 ID와 IDOR 방어의 관계로 알맞은 것은?

- ① ID 노출 여부와 별개로 서버가 인증된 사용자와 대상 자료의 접근 권한을 검사해야 한다.
- ② ID를 숨기면 소유권 검사를 모두 생략해도 된다.
- ③ ID가 숫자이면 자동으로 IDOR 공격이 막힌다.
- ④ 로그인 응답에 ID가 있으면 모든 API가 무조건 취약하다.

**정답:** ①

**해설:** 식별자는 권한 증명이 아니다. 요청의 대상 ID를 신뢰하지 않고 인증 주체의 권한·소유권을 확인한다.

### Q23-10. HttpSession을 Service에 직접 넘기지 않는 설계의 이점은?

- ① Service가 로그인 검증을 할 수 없어진다.
- ② Controller가 모든 DB 트랜잭션을 직접 구현해야 한다.
- ③ 세션을 넘기지 않으면 인증 사용자 ID도 전달할 수 없다.
- ④ HTTP 세션 관리를 웹 계층에 두고 업무 Service의 Servlet 결합과 테스트 부담을 줄인다.

**정답:** ④

**해설:** 웹 상태 관리와 업무 처리를 구분한다. Service에는 검증된 행위자·입력·결과 같은 업무 자료를 전달한다.

### Q23-11. 로그인 실패에서 이메일 없음과 비밀번호 오류를 같은 응답으로 처리하는 이유는?

- ① 응답 차이를 이용한 계정 존재 추측을 줄이기 위해서다.
- ② 사용자가 모든 관리자 비밀번호를 알아야 하기 때문이다.
- ③ 같은 메시지면 모든 인증 공격이 완전히 사라지기 때문이다.
- ④ DB에 존재하는 이메일을 실패 응답에 모두 나열하기 위해서다.

**정답:** ①

**해설:** 일관된 오류 메시지 외에도 응답 시간·시도 제한·로그 정책 등 계정 추측 경로를 검토한다.

### Q23-12. 로그인 성공 직후 세션 ID를 재발급하는 이유는?

- ① 세션 ID가 비밀번호 해시를 대체하기 때문이다.
- ② 공격자가 로그인 전에 정한 세션 ID를 재사용하는 세션 고정 공격을 줄이기 위해서다.
- ③ 재발급하면 CSRF·XSS 등 모든 공격도 자동 제거되기 때문이다.
- ④ 모든 로그인 사용자가 같은 세션 ID를 공유해야 하기 때문이다.

**정답:** ②

**해설:** 인증 전후 세션 식별자를 바꾸고 필요한 세션 속성·쿠키 정책을 유지한다. 다른 보안 방어도 별도로 필요하다.

### Q23-13. 비밀번호 변경 후 기존 세션·토큰에 대한 안전한 정책은?

- ① 비밀번호를 바꾸면 모든 JWT가 구현 없이 자동 폐기된다.
- ② 탈취된 기존 세션을 항상 영구 허용한다.
- ③ 기존 인증 상태의 무효화·토큰 버전·재인증 정책을 정하고 실제 적용 여부를 검증한다.
- ④ 로그아웃 화면만 표시하고 서버 상태는 유지한다.

**정답:** ③

**해설:** 세션과 JWT의 무효화 방법은 다르다. 저장소·버전·만료 등 선택한 정책으로 이전 인증 자료의 사용을 제한한다.

### Q23-14. 로그인 조회와 비밀번호 변경의 트랜잭션 설정을 구분한 이유는?

- ① readOnly=true는 모든 환경에서 INSERT·UPDATE를 반드시 차단하는 권한 기능이다.
- ② 비밀번호를 변경해도 읽기 전용 힌트만 유지해야 한다.
- ③ readOnly 설정이 BCrypt 계산을 자동 수행한다.
- ④ 조회 업무에는 readOnly 힌트를, 해시 갱신 업무에는 쓰기 트랜잭션을 적용한다.

**정답:** ④

**해설:** readOnly는 조회 의도를 나타내는 최적화 힌트이며 강제 보안 장치로 가정하지 않는다. 쓰기 경로의 실제 저장을 검증한다.

### Q23-15. AuthService가 Servlet API를 직접 다루지 않게 하는 이유는?

- ① 인증 업무를 HTTP 환경과 분리해 단위 테스트와 다른 호출 경로에서 재사용하기 위해서다.
- ② 비밀번호 비교를 Controller의 문자열 ==로 옮기기 위해서다.
- ③ HTTP 정보가 없으면 어떤 사용자도 검증할 수 없기 때문이다.
- ④ 업무 계층에서 역할과 인증 결과를 모두 제거하기 위해서다.

**정답:** ①

**해설:** 입력·검증·업무 결과와 세션 생성·폐기를 분리한다. Service는 Servlet 요청 객체 없이도 테스트할 수 있다.

## 24. 부서 Service — CRUD + 삭제 정책 (PRD 2.5.3, TRD 3.7.3)

**처음 배우는 개념 · 삭제 정책과 참조 관계**

- **어떤 기술인가요?** 참조 관계는 직원이 부서 ID를 가리키는 연결입니다.
- **왜 쓰나요?** 직원이 속한 부서를 지워 소속 정보가 끊기는 일을 막습니다.
- **어떻게 동작하나요?** Service가 역할·부서명 중복을 확인해 생성·수정하고 삭제 전 소속 직원 존재 여부를 검사합니다. 동시 요청까지 고려한 최종 무결성은 DB 제약과 함께 다룹니다.

파일: `starter/24-department-service/DepartmentService.java`

**4지선다 문제**

### Q24-01. 부서명 중복 방어로 알맞은 조합은?

- ① Service exists 검사와 DB unique 제약을 함께 적용한다.
- ② Service 검사만으로 모든 동시 요청을 보장한다.
- ③ DB unique가 있으면 오류 응답 정책이 불필요하다.
- ④ 부서명을 매번 무작위로 바꾸고 중복 여부를 무시한다.

**정답:** ①

**해설:** 사전 검사는 사용자 오류 안내에, DB 제약은 경합 시 무결성 보장에 필요하다.

### Q24-02. 소속 직원이 있는 부서를 삭제할 때 필요한 것은?

- ① 외래키를 무시하고 직원 정보는 고아 데이터로 둔다.
- ② 거부·이동·NULL 허용 중 정책을 정하고 참조 무결성을 유지한다.
- ③ 소속 직원을 아무 조건 없이 모두 퇴사시킨다.
- ④ GET 목록을 열면 부서를 자동 삭제한다.

**정답:** ②

**해설:** 삭제 정책은 직원 관계의 필수 여부와 업무 요구에 맞춰 명시해야 한다.

### Q24-03. 부서 상세와 소속 직원 조회에서 N+1을 줄이는 방법은?

- ① LAZY만 붙이면 언제나 단일 쿼리다.
- ② 직원을 한 명씩 반복 조회하면 가장 적은 쿼리다.
- ③ 필요한 관계를 fetch join·EntityGraph·DTO 조회 등으로 가져오고 쿼리 수를 확인한다.
- ④ 직원 ID 대신 이름 문자열을 저장하면 N+1이 자동 해결된다.

**정답:** ③

**해설:** 응답에 필요한 관계를 조회 단계에서 설계하고 실제 SQL 횟수를 검증한다.

### Q24-04. 부서 수가 매우 많아졌을 때 전체 목록 조회의 대안은?

- ① 항상 모든 부서와 모든 직원을 응답한다.
- ② 부서 데이터가 늘면 비밀번호 검증을 제거한다.
- ③ 클라이언트가 멈춰도 전체 조회를 유지한다.
- ④ 검색·페이징과 응답 크기 제한을 도입한다.

**정답:** ④

**해설:** 작은 기준정보의 단순 전체 조회도 규모가 커지면 조회량·전송량 정책을 바꿔야 한다.

### Q24-05. 부서 목록이 커질 때 List와 Page 선택을 재검토하는 기준은?

- ① 예상 데이터 규모·응답 크기·탐색 요구를 보고 커지면 페이징·검색을 적용한다.
- ② 부서라는 이름의 데이터는 언제나 건수가 적다.
- ③ 1,000건이 넘어도 전체 조회 비용은 반드시 일정하다.
- ④ List 반환이 모든 N+1 문제를 자동 제거한다.

**정답:** ①

**해설:** 초기 규모에 맞는 단순 조회도 데이터가 증가하면 재검토한다. 측정한 비용과 사용자 탐색 흐름을 기준으로 선택한다.

### Q24-06. 직원이 속한 부서를 삭제할 때 가능한 정책 조합은?

- ① 정책 없이 직원을 전부 삭제한다.
- ② 삭제 거절·대체 부서로 이동·관계 null 허용을 업무 규칙과 외래키 제약에 맞춰 선택한다.
- ③ 외래키가 있어도 존재하지 않는 부서 ID를 그대로 유지한다.
- ④ null을 허용하지 않는 관계에서 아무 처리 없이 부서만 지운다.

**정답:** ②

**해설:** 각 정책의 인사 이력·관계 제약·원자성 영향을 검토한다. 기본 부서 이동이나 null 허용은 실제 요구·매핑 변경과 함께 적용한다.

### Q24-07. 부서 상세의 직원 정보를 N+1 없이 가져오는 조회 설계는?

- ① LAZY를 EAGER로 바꾸면 모든 경우에 N+1이 사라진다.
- ② 직원마다 별도 쿼리를 실행해야만 N+1이 줄어든다.
- ③ 필요한 관계를 fetch join·EntityGraph 또는 DTO 전용 조회로 가져오고 실제 SQL 수를 확인한다.
- ④ JSON 직렬화 때 모든 관계를 무조건 로딩한다.

**정답:** ③

**해설:** 조회 범위·페이지 처리·컬렉션 중복을 고려해 방식을 선택한다. 어노테이션 이름만으로 성능을 보장하지 않는다.

## 25. 부서 Controller + DTO (TRD 3.7.3)

**처음 배우는 개념 · 부서 API와 요청 DTO**

- **어떤 기술인가요?** 부서 Controller는 부서 관리 HTTP 요청을 Service 호출로 바꿉니다.
- **왜 쓰나요?** 주소 처리·입력 형식 검사와 부서 중복·삭제 정책을 분리합니다.
- **어떻게 동작하나요?** 경로의 부서 ID와 검증한 요청 DTO를 받고 Service를 호출합니다. 조회는 결과를 보내고 삭제는 본문 없는 응답으로 완료를 알립니다.

파일: `starter/25-department-controller/DepartmentController.java`

**4지선다 문제**

### Q25-01. @PreAuthorize와 Service 가드를 함께 사용할 때 올바른 설명은?

- ① 어노테이션을 주석으로 적기만 하면 인가가 활성화된다.
- ② Service 검사는 언제나 불필요하다.
- ③ 화면 버튼 이름이 역할 검사를 대신한다.
- ④ Security가 실제 설정된 경우 진입점 인가와 업무 경계 검증을 함께 수행한다.

**정답:** ④

**해설:** 다층 검증을 하되 보안 설정과 메서드 인가 활성화도 실제로 확인해야 한다.

### Q25-02. PUT과 PATCH의 일반적인 차이는?

- ① PUT은 조회만, PATCH는 로그인만 가능하다.
- ② PATCH는 검증 없이 모든 필드를 바꿔야 한다.
- ③ PUT은 대상 표현의 교체, PATCH는 부분 변경을 나타내며 API 계약을 명시한다.
- ④ 둘은 언제나 요청 필수 필드와 의미가 완전히 같다.

**정답:** ③

**해설:** 메서드 이름만으로 구현이 완성되지 않으므로 갱신 범위와 필드 정책을 정의한다.

### Q25-03. 부서 상세에 소속 직원까지 넣는 응답 DTO 설계로 알맞은 것은?

- ② DepartmentDetailResponse에 필요한 직원 요약 DTO 목록을 포함한다.

**정답:** ②

### Q25-04. 부서는 List, 직원은 Page로 조회하는 선택 기준은?

- ② List는 관리자, Page는 일반 사용자 역할을 뜻한다.
- ③ JPA는 부서에 Page 사용을 금지한다.
- ④ 직원은 작은 목록이어도 모든 요구에서 Page만 허용된다.

**정답:** ①

**해설:** 자원 이름보다 실제 규모와 사용자 흐름을 기준으로 응답 형태를 선택하며 커질 때 재검토한다.

### Q25-05. 부서 수정에서 PUT·PATCH를 선택할 때 적절한 판단은?

- ③ 메서드 선택으로 권한 검사가 자동 사라진다.
- ④ 전체 교체와 일부 필드 변경 중 어떤 요청 계약인지 정하고 생략 필드의 의미를 문서·코드와 맞춘다.

**정답:** ④

**해설:** 부분 갱신 의도에는 PATCH가 자연스럽다. 이미 정의된 API 계약을 바꾸는 경우 클라이언트와 검증도 함께 갱신한다.

### Q25-06. 부서 응답에서 Employee 대신 MemberItem nested record를 두는 이유는?

- ② record는 비밀번호를 자동 마스킹하기 때문이다.
- ③ 상세 화면에 필요한 직원 필드만 공개하고 응답 전용 구조를 한곳에 모으기 위해서다.
- ④ Employee의 모든 필드와 관계를 그대로 응답하기 위해서다.

**정답:** ③

**해설:** DTO 공개 범위를 명시한다. 내부 record의 위치는 응답 구조 관리 선택이며 자동 보안 기능이 아니다.

## 26. 공지 Controller + DTO (TRD 3.7.5)

**처음 배우는 개념 · 공지 API와 역할 검사**

- **어떤 기술인가요?** 공지 Controller는 목록·상세·관리 요청의 입구입니다.
- **왜 쓰나요?** 조회 기능과 관리자 편집 기능에 다른 접근 기준을 적용합니다.
- **어떻게 동작하나요?** 경로·본문·현재 사용자 정보를 받아 공지 Service로 넘깁니다. 화면에서 편집 버튼을 숨겨도 직접 요청할 수 있으므로 서버에서 역할을 검사해야 합니다.

**4지선다 문제**

### Q26-01. GET 공지 상세에서 조회수를 변경할 때 고려할 점은?

**정답:** ②

**해설:** GET의 조회 의미와 변경 부작용을 구분하여 중복 증가 및 동시성을 설계한다.

### Q26-02. 공지 목록에 긴 본문을 모두 포함하는 비용과 대안은?

- ① 전송량·조회 비용이 커질 수 있으므로 목록에는 요약, 상세에는 본문을 제공한다.
- ② 본문이 길수록 네트워크 응답 크기는 줄어든다.
- ③ 본문을 포함하면 DB 조회가 항상 사라진다.
- ④ 본문 대신 평문 비밀번호를 보내는 것이 효율적이다.

**정답:** ①

**해설:** 목록과 상세의 사용 목적에 맞춰 공개 필드를 나눈다.

### Q26-03. @PageableDefault의 주된 역할은?

- ① 클라이언트의 모든 페이지 크기를 자동으로 최대값 이하로 제한한다.
- ② DB 비밀번호를 자동 생성한다.
- ③ 공지 작성자의 권한을 결정한다.
- ④ 페이지 요청의 기본 크기·정렬 등을 지정한다.

**정답:** ④

**해설:** 기본값 지정과 최대 페이지 크기 제한은 별도로 관리해야 한다.

### Q26-04. 공지 GET 상세의 조회수 증가 부작용을 검토한 설명으로 알맞은 것은?

- ① GET 요청은 사람이 버튼을 누를 때만 발생한다.
- ② GET 이름이면 DB의 증가 SQL이 읽기 전용으로 바뀐다.
- ③ 봇·미리보기·재시도로 증가할 수 있어 조회수 기록과 중복 집계 정책을 분리할 수 있다.
- ④ 요청 메서드만 바꾸면 봇 탐지가 자동 완성된다.

**정답:** ③

**해설:** HTTP 조회 의도와 집계 부작용을 구분한다. 이 실습의 구현과 개선 대안을 함께 이해한다.

### Q26-05. 이 실습의 공지 수정 메서드와 부분 변경의 관계를 올바르게 설명한 것은?

- ① 부분 수정 코드를 썼으므로 @PutMapping도 자동으로 PATCH가 된다.
- ② 현재 @PutMapping 계약은 확인하고 부분 변경으로 설계할 경우 PATCH와 필드 의미를 함께 조정한다.
- ③ GET으로 본문을 변경하는 것이 이 실습의 수정 계약이다.
- ④ PUT이면 기존 본문과 생략 필드의 의미를 확인하지 않아도 된다.

**정답:** ②

**해설:** 현재 PRD·Controller의 PUT 계약과 부분 변경 설계의 대안을 구분한다. 계약 변경 시 구현·문서·테스트를 맞춘다.

### Q26-06. 공지 목록 응답에 모든 content를 넣으면 발생할 수 있는 비용은?

- ① 각 본문 길이만큼 응답량·전송·렌더링 비용이 커져 요약 목록과 상세 응답을 분리할 수 있다.
- ② 본문을 넣으면 모든 조회가 반드시 한 SQL로 줄어든다.
- ③ content가 길어도 JSON 응답 크기는 항상 같다.
- ④ 본문을 생략하면 권한 검사가 자동 완료된다.

**정답:** ①

**해설:** 목록에 필요한 공개 필드만 전달하고 본문은 상세 조회로 제공하는 방식을 규모에 맞춰 검토한다.

## 27. 결재 Controller + DTO — my / pending / submit / approve / reject (TRD 3.7.6)

### Q27-02. submit·approve·reject를 별도 동작으로 표현하는 이유는?

- ① 모든 상태 변경을 클라이언트에 맡기기 위해서다.
- ② 각 동작의 행위자·출발 상태·결과를 명확히 검증하기 위해서다.
- ③ 별도 경로를 만들면 Service가 필요 없어지기 때문이다.

**정답:** ②

**해설:** 명시적인 업무 동작은 상태값 임의 변경에 비해 정책을 드러내기 쉽다.

- ③ APPROVER 또는 ADMIN 역할 중 하나를 가진 사용자만 허용한다.
- ④ 작성자이면 역할과 무관하게 자동 허용한다.

**정답:** ③

**해설:** Security의 역할 인가는 문서별 지정 결재자 검사와 별도로 적용한다.

### Q27-04. 결재 /my와 /pending 조회의 권한 범위를 짝지은 것은?

- ① my는 모든 직원의 문서, pending은 로그인 없이 전체 문서다.
- ② 요청의 writerId만 신뢰해 다른 사람의 my 문서를 보여준다.
- ③ ADMIN 문자열이 본문에 있으면 모든 pending 문서를 보여준다.
- ④ my는 인증된 작성자의 문서, pending은 역할 검사를 통과한 지정 결재자의 대기 문서다.

**정답:** ④

**해설:** 인증 주체를 기준으로 작성자·결재자 조건을 쿼리에 적용한다. 역할과 상태 조건도 함께 검증한다.

### Q27-05. 작성 직후 자동 제출하지 않고 별도 submit API를 두는 이유는?

- ① 임시저장·수정·검토 후 사용자가 결재 요청을 확정하는 시점을 구분하기 위해서다.
- ② 임시저장 상태에서도 승인 완료로 처리하기 위해서다.
- ③ 결재자 검사를 생략하기 위해서다.
- ④ submit이 자료 소유권을 자동으로 알아서 검사하기 때문이다.

**정답:** ①

**해설:** DRAFT와 PENDING의 의미에 맞게 요청 흐름과 상태 전이를 분리하며 제출 권한도 검사한다.

### Q27-06. 지정 결재자가 아닌 사용자의 pending 접근을 막는 방법은?

- ① 클라이언트가 보낸 approverId가 자신의 것이라고 믿는다.

## 28. 직원 상세 / 수정 / 퇴사 처리 (PRD 2.5.2)

**정답:** ①

**해설:** 지연 관계 접근 시점과 SQL 발생을 확인해야 LazyInitializationException과 과도한 조회를 피할 수 있다.

### Q28-02. 직원의 부서를 변경하는 올바른 순서는?

- ① 존재하지 않는 부서 ID를 그대로 넣는다.
- ② 대상 부서 존재 확인 후 changeDepartment 같은 도메인 메서드로 변경한다.
- ③ 부서명만 바꾸고 외래키는 기존 값을 유지한다.
- ④ 응답 DTO만 수정하면 저장 정보도 바뀐다.

**정답:** ②

**해설:** 관계 대상의 유효성과 도메인 변경 규칙을 함께 보장한다.

### Q28-03. Service에서 임의 setter 대신 도메인 메서드를 사용하는 이유는?

- ① 메서드 이름을 바꾸면 테스트가 필요 없어지기 때문이다.
- ② 모든 검증을 Controller 밖에서 제거하기 위해서다.
- ③ 변경의 의미와 불변 조건을 Entity 경계에 모으기 위해서다.
- ④ DB 컬럼 이름을 자동으로 암호화하기 위해서다.

**정답:** ③

**해설:** 도메인 메서드는 상태 변경을 업무 동작으로 표현하고 잘못된 변경 경로를 줄인다.

### Q28-04. 퇴사 상태 처리와 물리 삭제의 차이로 알맞은 것은?

- ① RESIGNED로 바꾸면 모든 과거 행도 삭제된다.

- ④ 상태 처리는 이력을 보존하고 조회·업무 자격 정책이 필요하며 물리 삭제는 참조·보존 정책을 검토해야 한다.

**정답:** ④

**해설:** 보존 요구와 참조 무결성, 일반 목록 필터 및 신규 업무 차단을 함께 고려한다.

### Q28-05. 직원 정보 변경을 도메인 메서드로 수행하는 이유는?

**4지선다 문제**

### Q38-01. 중복 승인·부분 저장·Entity 노출·지연 로딩·동시 가입 문제를 다룰 때 알맞은 원칙은?

- ① 모든 문제를 CSS 수정으로 해결한다.
- ② 오류를 무시하고 성공 응답을 반환한다.
- ③ 코드 전체를 동시에 바꿔 원인 검증을 생략한다.
- ④ 각 문제의 재현과 원인을 확인하고 상태·원자성·응답·조회·DB 제약을 알맞은 경계에서 수정한다.

**정답:** ④

**해설:** 겉으로 비슷한 실패도 원인이 다르므로 증거에 맞춰 필요한 책임을 수정한다.

### Q38-02. 트러블슈팅 기록으로 가장 적절한 것은?

- ② 오류 로그를 지운 사실만 기록한다.
- ③ 실패 입력·로그 → 원인 근거 → 최소 수정 → 같은 명령과 회귀 테스트 결과·배운 점
- ④ 관련 없는 기술 용어만 나열한다.

**정답:** ③

### Q38-03. 본인의 트러블슈팅 사례를 추가할 때 필요한 근거는?

- ③ 다른 사람의 코드만 복사하고 출처·적용 결과는 생략한다.
- ④ 문제 이름만 적고 구현 근거는 남기지 않는다.

**정답:** ②

**해설:** 본인 프로젝트에서 검증 가능한 사실을 연결해야 취업 증거로 사용할 수 있다.

## 39. 면접 카드 + 커밋 + PR 템플릿 (TRD 3.18 ~ 3.20)

**처음 배우는 개념 · Git·커밋·PR**

- **어떤 기술인가요?** Git은 변경 이력을 관리하고 커밋은 변경 묶음, PR은 변경을 검토하고 합치기 위한 요청입니다.
- **왜 쓰나요?** 기능이 왜 바뀌었고 무엇으로 검증했는지 다른 사람이 추적하도록 합니다.
- **어떻게 동작하나요?** 변경을 확인하고 한 가지 의도의 커밋으로 기록합니다. PR에는 문제·변경 결과·검증을 쓰고 면접에서는 해당 코드와 테스트를 근거로 선택 이유를 설명합니다.

파일: `starter/39-interview-and-commit/InterviewAndCommit.md`

**4지선다 문제**

### Q39-01. 기술 면접 답변에서 가장 적절한 구성은?

- ① 기술 이름만 많이 나열한다.
- ② 미구현 기능을 완료했다고 말한다.
- ③ 모든 질문에 같은 외운 정의만 답한다.
- ④ 문제·선택 이유·대안·실제 코드와 테스트 근거를 짧게 연결한다.

**정답:** ④

**해설:** 설계 선택과 실제 결과를 근거로 설명해야 구현 이해를 보여줄 수 있다.

### Q39-02. 버그 수정·문서 변경·테스트 추가 커밋 타입의 올바른 조합은?

- ① feat, style, chore만 사용한다.
- ② docs, feat, fix 순서로 사용한다.
- ③ fix, docs, test
- ④ 어떤 변경이든 merge만 사용한다.

**정답:** ③

**해설:** feat는 새 기능, fix는 버그 수정, docs는 문서, test는 테스트 변경을 표현한다.

### Q39-03. 커밋 메시지 본문에 적을 내용으로 알맞은 것은?

- ① diff에 보이는 모든 줄을 그대로 반복한다.
- ② 변경 이유와 선택 의도를 적고 한 커밋에 한 가지 의도를 담는다.
- ③ 여러 무관한 기능을 섞고 이유는 생략한다.
- ④ 평문 비밀번호와 세션 쿠키를 기록한다.

**정답:** ②

**해설:** 무엇이 바뀌었는지는 diff가 보여주므로 이유와 판단을 남기면 리뷰에 도움이 된다.

### Q39-04. PR 설명에서 빠뜨리지 않아야 할 기본 항목은?

- ① 무엇이 바뀌었는지·왜·검증 방법과 결과·영향 범위
- ② 작성자의 취미·좋아하는 색·날씨·비밀번호
- ③ 커밋 개수만 기록한다.
- ④ 스크린샷만 붙이고 동작과 검증은 생략한다.

**정답:** ①

**해설:** 대화를 모르는 리뷰어가 문제·결과·검증·영향을 판단할 수 있게 작성한다.

### Q39-05. 이 프로젝트를 만든 이유에 대한 적절한 답변은?

- ① 기술 이름을 많이 쓰면 실제 동작은 필요 없기 때문에 만들었다.
- ② 사용자 비밀번호를 조회하기 위해 만들었다.
- ③ 모든 업무를 단일 Controller에 넣는 연습을 위해 만들었다.
- ④ 직원·부서·휴가·결재 흐름을 구현하며 업무 규칙·권한·검증 역량을 보여주기 위해 만들었다.

**정답:** ④

**해설:** 프로젝트 목적을 실제 업무 시나리오와 구현·검증 결과에 연결한다.

### Q39-06. 면접에서 User와 Employee를 분리한 이유로 알맞은 것은?

- ① 두 객체의 ID 숫자를 반드시 같게 만들기 위해서다.
- ② Employee에서 모든 비밀번호를 직접 검증하기 위해서다.
- ③ 계정 인증과 인사 정보의 책임·변경 주기가 다르기 때문이다.
- ④ 계정 권한 변경을 모든 부서 이름 변경과 함께 처리하기 위해서다.

**정답:** ③

**해설:** 인증 관심사와 업무 데이터의 생명주기를 나누면 변경 영향을 줄일 수 있다.

### Q39-07. 직원과 부서의 관계 설계에 대한 적절한 설명은?

- ① 직원마다 반드시 새로운 부서를 하나 생성했다.
- ② 여러 직원이 한 부서에 속하는 N:1이며 LAZY와 필요한 조회 전략을 함께 검토했다.
- ③ LAZY만 쓰면 모든 SQL이 사라지므로 조회 테스트를 생략했다.
- ④ 외래키 없이 이름 길이가 같으면 같은 부서로 처리했다.

**정답:** ②

**해설:** 데이터 관계와 실제 조회 비용을 함께 설명해야 설계 근거가 된다.

### Q39-08. 휴가 상태 관리에 대한 적절한 설명은?

- ① enum과 도메인 메서드로 PENDING에서 승인·반려하는 허용 전이를 검사했다.
- ② 자유로운 문자열을 요청자가 원하는 대로 저장했다.
- ③ Controller 응답의 색상만 바꿔 승인 상태를 표현했다.
- ④ 이미 승인된 휴가도 아무 권한 없이 반복 승인하도록 했다.

**정답:** ①

**해설:** 상태 모델은 허용 동작과 실패 조건을 코드로 보장하고 테스트로 확인한다.

### Q39-09. @Transactional을 적용한 이유에 대한 적절한 답변은?

- ① HTTP 요청을 무조건 관리자 요청으로 바꾸기 위해 적용했다.
- ② 모든 동시성 문제가 자동으로 해결되기 때문에 별도 검증을 하지 않았다.
- ③ HTML 출력 글꼴을 통일하기 위해 적용했다.
- ④ User·Employee 동시 생성과 승인 변경 같은 업무 단위의 원자성을 보장하기 위해 적용했다.

**정답:** ④

**해설:** 트랜잭션은 업무 변경의 함께 성공·실패를 보장하며 동시성 제어와 구분해서 설명한다.

### Q39-10. Entity 대신 응답 DTO를 사용한 이유에 대한 적절한 답변은?

- ① DTO는 모든 비밀번호를 자동으로 해시하므로 필드 검토가 필요 없기 때문이다.
- ② DTO를 반환하면 모든 DB 오류가 사라지기 때문이다.
- ③ Entity의 모든 관계와 비밀번호를 그대로 내보내기 위해서다.
- ④ 민감 필드 공개를 제한하고 지연 로딩·API 계약을 명시적으로 관리하기 위해서다.

**정답:** ④

**해설:** DTO 공개 필드는 직접 설계하며 조회·매핑 시점도 검증해야 한다.

### Q39-11. 관리자와 일반 사용자의 권한 구분에 대한 적절한 답변은?

- ① 신뢰할 수 있는 인증 역할을 서버에서 검사하고 자료 소유권·업무 가드를 함께 검증했다.
- ② 화면 버튼만 숨기면 직접 API 호출도 막힌다.
- ③ 요청 본문에 ADMIN이라고 쓰면 관리자로 처리했다.
- ④ 한 번 로그인하면 모든 사용자가 모든 자료를 수정하도록 했다.

**정답:** ①

**해설:** 역할 기반 인가와 개별 자료 접근 규칙을 코드와 권한 실패 테스트로 설명한다.

### Q39-12. 가장 어려웠던 문제의 해결을 설명하는 적절한 방식은?

- ① 오류를 경험하지 않았어도 해결했다고 주장한다.
- ② 실제 실패·원인 근거·수정·재검증과 배운 점을 연결해 설명한다.
- ③ 관련 기술 이름만 나열하고 결과는 생략한다.
- ④ 로그와 테스트를 모두 지운 뒤 문제가 없었다고 답한다.

**정답:** ②

**해설:** 검증 가능한 본인 사례를 짧은 흐름으로 설명하고 코드·커밋·테스트 근거를 제시한다.

### Q39-13. 사내 업무관리 시스템의 중요한 기능을 설명하는 적절한 기준은?

- ① 화면의 색상만으로 모든 업무 기능의 중요도를 정한다.
- ② 검증 없이 CRUD 개수만 많으면 충분하다고 답한다.
- ③ 권한·상태 전이·데이터 일관성이 연결된 업무 흐름과 사용자 요구를 근거로 설명한다.
- ④ 실제 요구와 관계없이 최신 기술 이름만 나열한다.

**정답:** ③

**해설:** 본인이 구현한 업무 흐름과 실패 방지 효과를 구체적인 근거로 설명한다.

### Q39-14. 승인·반려 기능에서 핵심 검증을 설명한 것은?

- ① 로그인 여부만 맞으면 모든 문서를 누구나 처리한다.
- ② 승인 버튼의 위치만 확인한다.
- ③ 반려 사유가 있으면 상태·행위자 검사를 생략한다.
- ④ 현재 상태, 처리 행위자·권한, 반려 사유 등 동작별 필수 조건을 확인한다.

**정답:** ④

**해설:** 허용된 사람의 허용된 상태 전이만 실행되도록 규칙과 실패 테스트를 연결한다.

### Q39-15. 공지 목록에서 페이징이 필요한 이유로 알맞은 것은?

- ① 조회량·응답 크기를 제한해 많은 공지를 효율적으로 탐색하게 한다.
- ② 페이징은 공지 작성자에게 관리자 역할을 부여한다.
- ③ 페이징을 쓰면 인증과 검증이 필요 없어진다.
- ④ 항상 전체 본문을 한 번에 보내는 것과 비용이 반드시 같다.

**정답:** ①

**해설:** 페이지 크기·정렬·검색을 실제 규모와 사용 흐름에 맞춰 설계한다.

### Q39-16. 전자결재 확장 계획에 대한 적절한 설명은?

- ① 요구 확인 없이 status 문자열을 무제한 추가한다.
- ② 다단계 결재·위임·감사 이력 등의 요구를 정하고 상태·권한·동시성·테스트 영향을 검토한다.
- ③ 이미 승인된 문서를 누구나 수정하게 한다.
- ④ 실제로 없는 확장 기능을 구현 완료라고 소개한다.

**정답:** ②

**해설:** 확장은 요구와 현재 구조의 한계를 근거로 계획하며 미구현 계획과 실제 결과를 구분한다.
