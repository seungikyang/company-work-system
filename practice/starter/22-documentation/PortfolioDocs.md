## 4지선다 문제

### Q22-01. 실행 프로젝트 README에 필요한 내용으로 가장 적절한 것은?

- ① 실행 불가능한 기능도 완료 목록에 넣는다.
- ② 비밀번호와 DB 비밀을 평문으로 적는다.
- ③ 목적·기술·구조·주요 기능·실행·API·검증·문제 해결과 실제 근거다.
- ④ 프로젝트 제목만 쓰고 실행 명령은 생략한다.

**정답:** ③

**해설:** 처음 보는 사람이 프로젝트를 실행·검증하고 구현 범위를 판단할 수 있어야 한다.

### Q22-02. ERD 문서 도구를 선택하는 적절한 기준은?

- ① 로고가 가장 화려한 도구를 반드시 쓴다.
- ② 테이블 관계를 표현할 수 없는 형식만 쓴다.
- ③ 어떤 방식이든 수정 후 실제 스키마와 비교하지 않는다.
- ④ 관계·키·제약을 명확히 표현하고 팀이 갱신·버전 관리할 수 있는 방식이다.

**정답:** ④

**해설:** 텍스트·그림·전용 도구 중 실제 데이터 구조와 일치하게 관리할 수 있는 방식을 고른다.

### Q22-03. 트러블슈팅 기록의 기본 순서로 알맞은 것은?

- ① 문제 → 원인 → 해결 → 배운 점
- ② 해결 → 성공 자랑 → 관련 없는 코드 → 비밀번호
- ③ 원인 없이 오류 메시지를 지운다.
- ④ 모든 사건을 같은 한 문장으로 기록한다.

**정답:** ①

**해설:** 재현 조건과 원인 근거·변경·재검증을 연결하면 해결 효과를 설명할 수 있다.

### Q22-04. API 명세를 Markdown 또는 OpenAPI로 작성할 때 지켜야 할 기준은?

- ① 자동 생성이면 구현과 일치하는지 확인할 필요가 없다.
- ② 실제 요청·응답·권한·오류와 명세가 일치하도록 갱신하고 검증한다.
- ③ 수동 명세에는 실패 응답을 적을 수 없다.
- ④ 도구 선택만으로 모든 업무 규칙 테스트가 끝난다.

**정답:** ②

**해설:** 작성 방식보다 실행 계약과 명세의 일치가 중요하다.

## 8. 심화 노트 (포트폴리오 완성도 포인트)

- **README 의 기준은 "클론한 사람이 5분 안에 실행"**: 실행 방법·기본 포트·H2 콘솔 경로·시드 계정(admin/employee)·샘플 요청을 명시한다. 면접관이 가장 먼저 보는 문서다.
- **트러블슈팅이 곧 면접 무기**: 문제→원인→해결→배운 점 4단 + 코드 diff 로 적으면 "가장 어려웠던 문제는?"(TRD 3.19 Q12) 답변이 그대로 나온다. 휴가 중복 승인(상태 검증 위치), 직원 부분 저장(@Transactional), LazyInitializationException(DTO 변환 시점)이 이 프로젝트의 대표 3건.
- **API 명세 진화**: 학습 초반은 손으로 적은 Markdown(필드 의미를 직접 사고), 후반은 `springdoc-openapi` 로 `/swagger-ui.html` 자동 생성 + 손 명세는 차이점만 유지. 1차 세션 구현은 **`JSESSIONID` 쿠키**, JWT 확장은 **`Authorization: Bearer ...`**처럼 실제 인증 전달 방식을 적는다.
- **면접 답변 카드는 STAR**(상황-과제-행동-결과)로 30초: User/Employee 분리, @Transactional 위치, Entity→DTO 분리, 상태 머신 캡슐화가 단골 질문. 각 답에 "왜" 와 "대안과의 트레이드오프" 를 한 줄씩 넣으면 깊이가 산다.
- **커밋/PR 도 포트폴리오**: "무엇" 이 아니라 "왜" 를 적은 커밋(feat/fix/refactor/docs/test), PR 4섹션(무엇/왜/테스트/영향)이 협업 역량을 보여준다(39장과 연결).
