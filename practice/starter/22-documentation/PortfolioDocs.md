## 4. API 명세 작성 방법

### A. 손으로 적기 (Markdown)

장점:
- diff 친화적, 코드와 함께 PR 리뷰 가능.
- 신입 단계에서 어떤 필드가 어떤 의미인지 직접 생각하게 된다.

단점:
- 실제 코드와 어긋날 수 있다.

### B. 자동 생성 (springdoc-openapi)

`build.gradle` 에 의존성 추가만으로 `/swagger-ui.html` 이 뜬다.

```groovy
implementation 'org.springdoc:springdoc-openapi-starter-webmvc-ui:____'
```

선택 기준:

- [ ] 학습 1~2주차: ____ 로 시작
- [ ] 학습 3~4주차: ____ 로 자동 생성하고, 손으로 적은 명세는 차이점만 유지

## 8. 심화 노트 (포트폴리오 완성도 포인트)

- **README 의 기준은 "클론한 사람이 5분 안에 실행"**: 실행 방법·기본 포트·H2 콘솔 경로·시드 계정(admin/employee)·샘플 요청을 명시한다. 면접관이 가장 먼저 보는 문서다.
- **트러블슈팅이 곧 면접 무기**: 문제→원인→해결→배운 점 4단 + 코드 diff 로 적으면 "가장 어려웠던 문제는?"(TRD 3.19 Q12) 답변이 그대로 나온다. 휴가 중복 승인(상태 검증 위치), 직원 부분 저장(@Transactional), LazyInitializationException(DTO 변환 시점)이 이 프로젝트의 대표 3건.
- **API 명세 진화**: 학습 초반은 손으로 적은 Markdown(필드 의미를 직접 사고), 후반은 `springdoc-openapi` 로 `/swagger-ui.html` 자동 생성 + 손 명세는 차이점만 유지. 어느 쪽이든 **인증 헤더 형식(`Authorization: Bearer ...`)** 을 반드시 적는다.
- **면접 답변 카드는 STAR**(상황-과제-행동-결과)로 30초: User/Employee 분리, @Transactional 위치, Entity→DTO 분리, 상태 머신 캡슐화가 단골 질문. 각 답에 "왜" 와 "대안과의 트레이드오프" 를 한 줄씩 넣으면 깊이가 산다.
- **커밋/PR 도 포트폴리오**: "무엇" 이 아니라 "왜" 를 적은 커밋(feat/fix/refactor/docs/test), PR 4섹션(무엇/왜/테스트/영향)이 협업 역량을 보여준다(39장과 연결).
