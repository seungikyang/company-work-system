이 챕터의 개념과 설계 판단을 4지선다로 확인합니다. [선택·채점 화면](../../../problems.html#problem-37)에서 풀고 실제 구현·검증 결과를 [통합 워크북](../../job-preparation-workbook.md)에 남깁니다.

## 챕터 계약

| 구분 | 완료 기준 |
|---|---|
| 학습 목표 | 업무 규칙을 DTO·Service·Entity·DB 중 알맞은 방어 계층에 배치한다. |
| 취업 결과물 | 핵심 업무 규칙의 1차 검증·최종 방어선·실패 테스트 매트릭스 |
| 완료 검증 | 모든 핵심 규칙에 성공 테스트와 최소 한 개의 실패 테스트를 연결한다. |

검증 위치 표기:
- **D** = DTO (Bean Validation)
- **E** = Entity (도메인 메서드)
- **S** = Service (비즈니스 흐름)
- **DB** = DB 제약 (unique, not null)

## 4지선다 문제

### Q37-01. 입력 형식·업무 조건·상태 전이·DB 무결성의 알맞은 검증 위치는?

- ① DTO·Service·Entity·DB에 각각 맞는 책임을 둔다.
- ② 모든 검증을 CSS에 둔다.
- ③ 모든 검증은 클라이언트가 했다고 믿는다.
- ④ DB는 모든 업무 권한을 자동 판단한다.

**정답:** ①

**해설:** 형식 검사와 업무·상태·최종 저장 제약은 서로 다른 실패를 막는다.

### Q37-02. 비슷한 검증을 여러 계층에 둘 수 있는 이유는?

- ① 같은 코드를 늘리는 것 자체가 목적이다.
- ② 다른 진입 경로와 동시 요청에서도 규칙·무결성을 보장하기 위해서다.
- ③ 검증을 반복하면 서로 다른 정책을 사용해도 괜찮다.
- ④ 여러 검증이 있으면 자동으로 모든 코드가 컴파일된다.

**정답:** ②

**해설:** 중복 방어의 책임을 구분하고 정책이 서로 충돌하지 않게 관리한다.

### Q37-03. Service exists 검사와 DB unique의 관계는?

- ① exists가 false이면 DB 제약이 절대로 필요 없다.
- ② unique는 HTML에만 적용된다.
- ③ exists는 사전 오류 안내, unique는 동시 요청의 최종 중복 방지다.
- ④ 둘 중 어느 것도 저장 무결성과 관계없다.

**정답:** ③

**해설:** 검사 직후 다른 요청이 저장할 수 있으므로 DB 제약을 함께 둔다.

### Q37-04. 도메인 상태 오류를 공통 ErrorCode로 응답하는 방법은?

- ① 어떤 예외든 무조건 로그인 성공으로 응답한다.
- ② IllegalStateException 메시지에 비밀번호를 넣는다.
- ③ 상태 오류가 나면 전체 DB를 삭제한다.
- ④ 예외 종류를 구분해 일관된 업무 코드로 변환하고 관련 실패 테스트를 둔다.

**정답:** ④

**해설:** 도메인 규칙과 외부 오류 계약을 명확히 연결하며 내부 장애를 업무 실패로 무분별하게 숨기지 않는다.

## 8. 심화 노트 (면접 답변 포인트)

- **다층 방어가 중복이 아닌 이유**: 각 층이 막는 실패 모드가 다르다. D(DTO)=형식이 틀린 요청을 빠르게 400 으로, S(Service)=상태/권한/관계 흐름, E(Entity)=어느 호출 경로로 와도 깨지지 않는 불변식, DB=동시성 race 까지. 한 층을 우회해도 다음 층이 잡는다.
- **"PENDING 검증을 Service 에만" 두면**: 다른 Service 메서드나 배치가 `leave.approve()` 를 직접 호출하는 경로가 생기면 그 검증을 빠뜨려 이미 승인된 휴가를 또 승인하는 버그가 재발한다(38장 트러블슈팅 1번). 그래서 도메인 메서드 안에 둔다.
- **exists + DB unique**: exists 는 "친절한 에러 메시지를 빨리" 주기 위한 UX 용, unique 는 "동시성에서도 보장" 하는 무결성 용. 둘은 역할이 달라 둘 다 둔다.
- **IllegalStateException → BusinessException 변환**: 도메인 메서드가 던진 `IllegalStateException` 을 그대로 두면 GlobalExceptionHandler 에서 ErrorCode 로 일관 매핑하기 어렵다. 도메인 경계에서 `BusinessException(INVALID_STATUS)` 로 변환하거나, 핸들러에 `IllegalStateException` 매핑을 추가한다.
- **Service 비대화 리팩터링**: 규칙이 늘면 ① 도메인 서비스(여러 엔티티에 걸친 규칙) ② 정책 객체(LeavePolicy 등) ③ Specification(동적 조회 조건) 으로 분리한다.
