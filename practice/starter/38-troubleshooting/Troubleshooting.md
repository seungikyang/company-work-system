# 트러블슈팅 워크북

TRD 3.16 의 트러블슈팅 형식을 따라, 사내 업무관리 시스템에서 자주 마주치는 문제 5건을 직접 채워봅니다. 면접에서 “문제 — 원인 — 해결 — 배운 점” 4단계로 답할 수 있게 됩니다.

각 항목은 직접 빈칸을 채워 본 뒤, `answers.md` 가 아니라 본인 머릿속의 답과 비교하세요.

## 1. 휴가 승인 상태 중복 처리 (TRD 3.16.1)

### 문제
이미 승인된 휴가를 다시 ____ 또는 ____ 할 수 있는 버그가 있었다.

### 원인
승인/반려 처리 전에 현재 상태가 ____ 인지 검증하지 않았다.
검증을 Service 에서만 하면, 도메인 메서드(`leave.approve()`)를 다른 경로에서 호출했을 때 동일 버그가 재발할 수 있다.

### 해결
- 검증을 ____ (Service / Entity) 안에 두어 상태 전이를 캡슐화했다.
- 통합 테스트로 "이미 APPROVED 인 휴가를 다시 승인" 시나리오를 추가했다.

### 배운 점
승인/반려처럼 상태 머신이 있는 도메인은 ____ 에서 전이를 캡슐화하는 편이 안전하다.

## 2. 직원 등록 중 일부 데이터만 저장됨 (TRD 3.16.2)

### 문제
직원 등록 시 ____ 는 생성되었지만 ____ 저장 도중 예외가 발생하면 사용자 계정만 남아 “계정은 있는데 직원 정보가 없는” 상태가 만들어졌다.

### 원인
User 생성과 Employee 생성이 같은 ____ 으로 묶이지 않았다.

### 해결
Service 메서드에 `@____` 을 적용해 두 저장이 원자적으로 처리되도록 묶었다.

### 배운 점
서로 연관된 데이터를 함께 저장할 때는 ____ 이 필수다. 트랜잭션이 없는 상태에서의 “일부 성공” 은 가장 디버깅하기 어렵다.

## 3. Entity 직접 반환으로 인한 보안 노출 (TRD 3.16.3)

### 문제
Controller 에서 User Entity 를 그대로 반환하니 응답에 ____ 가 노출되었고, LAZY 프록시 직렬화 실패와 JSON 무한 루프도 발생했다.

### 원인
응답 모양을 도메인에 의존시켰다. Entity 가 ____ 의 책임까지 떠안았다.

### 해결
- 응답 DTO 를 별도 record 로 분리.
- `EmployeeResponse.from(employee)` 같은 정적 팩토리로 변환.
- Entity 에는 어떤 직렬화 어노테이션도 두지 않음.

### 배운 점
Entity 와 DTO 분리는 보안 + 직렬화 + ____ 안정성을 동시에 챙겨준다.

## 4. LazyInitializationException — “open-in-view” 와 직렬화 시점

### 문제
직원 목록을 응답 변환할 때 `e.getDepartment().getName()` 에서 `LazyInitializationException` 이 발생했다.

### 가능한 원인 후보
- Repository 가 LAZY 로 불러온 연관관계를 Service 메서드 밖(트랜잭션 종료 후)에서 접근했다.
- `spring.jpa.open-in-view` 가 ____ 로 꺼져 있어 view 렌더링 시점에 세션이 닫혀 있었다.

### 해결 옵션 (장단점 적기)
1. fetch join 으로 미리 로드 — 장점: 정직. 단점: ____
2. Service 안에서 DTO 까지 변환해 반환 — 장점: ____ 단점: Service 가 응답 모양에 의존.
3. `open-in-view: true` 로 두기 — 장점: 편함. 단점: 트랜잭션 경계가 모호해진다.

### 배운 점
LAZY 의 비용은 “언제 어디서 SELECT 가 나가는지 추적이 어렵다” 이다. ____ 시점에 어떤 데이터를 쓸지 미리 결정해야 한다.

## 5. 같은 이메일 동시 가입 race condition

### 문제
사용자 두 명이 같은 이메일로 동시에 가입 버튼을 누르면, `existsByEmail` 검사를 둘 다 통과하고 둘 다 저장에 성공해 ____ 가 깨질 뻔했다.

### 원인
애플리케이션 레벨의 `existsByEmail` 검사는 race condition 을 ____.

### 해결
- DB 의 `____` 제약을 1차 방어선으로 두어 결국 한쪽만 저장에 성공하도록 함.
- 두 번째 시도는 `DataIntegrityViolationException` 으로 떨어지고, 그것을 GlobalExceptionHandler 에서 `DUPLICATE_EMAIL` 로 변환.

### 배운 점
애플리케이션 검증과 DB 제약은 ____ 관계가 아니라 다층 방어다. 동시성이 있는 곳에서는 항상 둘 다 둔다.
