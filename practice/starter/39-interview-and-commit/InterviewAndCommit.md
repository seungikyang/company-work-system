## 챕터 계약

| 구분 | 완료 기준 |
|---|---|
| 학습 목표 | 구현 선택과 트레이드오프를 코드 근거가 있는 30초 답변으로 압축한다. |
| 취업 결과물 | 핵심 면접 카드 8개와 한 의도의 커밋·리뷰 가능한 PR 설명 |

## 4지선다 문제

### Q39-01. 기술 면접 답변에서 가장 적절한 구성은?

- ① 기술 이름만 많이 나열한다.
- ② 미구현 기능을 완료했다고 말한다.
- ③ 모든 질문에 같은 외운 정의만 답한다.
- ④ 문제·선택 이유·대안·실제 코드와 테스트 근거를 짧게 연결한다.

**정답:** ④

**해설:** 설계 선택과 실제 결과를 근거로 설명해야 구현 이해를 보여줄 수 있다.

### Q39-02. 버그 수정·문서 변경·테스트 추가 커밋 타입의 올바른 조합은?

- ① feat, style, chore만 사용한다.
- ② docs, feat, fix 순서로 사용한다.
- ③ fix, docs, test
- ④ 어떤 변경이든 merge만 사용한다.

**정답:** ③

**해설:** feat는 새 기능, fix는 버그 수정, docs는 문서, test는 테스트 변경을 표현한다.

### Q39-03. 커밋 메시지 본문에 적을 내용으로 알맞은 것은?

- ① diff에 보이는 모든 줄을 그대로 반복한다.
- ② 변경 이유와 선택 의도를 적고 한 커밋에 한 가지 의도를 담는다.
- ③ 여러 무관한 기능을 섞고 이유는 생략한다.
- ④ 평문 비밀번호와 세션 쿠키를 기록한다.

**정답:** ②

**해설:** 무엇이 바뀌었는지는 diff가 보여주므로 이유와 판단을 남기면 리뷰에 도움이 된다.

### Q39-04. PR 설명에서 빠뜨리지 않아야 할 기본 항목은?

- ① 무엇이 바뀌었는지·왜·검증 방법과 결과·영향 범위
- ② 작성자의 취미·좋아하는 색·날씨·비밀번호
- ③ 커밋 개수만 기록한다.
- ④ 스크린샷만 붙이고 동작과 검증은 생략한다.

**정답:** ①

**해설:** 대화를 모르는 리뷰어가 문제·결과·검증·영향을 판단할 수 있게 작성한다.

### Q39-05. 이 프로젝트를 만든 이유에 대한 적절한 답변은?

- ① 기술 이름을 많이 쓰면 실제 동작은 필요 없기 때문에 만들었다.
- ② 사용자 비밀번호를 조회하기 위해 만들었다.
- ③ 모든 업무를 단일 Controller에 넣는 연습을 위해 만들었다.
- ④ 직원·부서·휴가·결재 흐름을 구현하며 업무 규칙·권한·검증 역량을 보여주기 위해 만들었다.

**정답:** ④

**해설:** 프로젝트 목적을 실제 업무 시나리오와 구현·검증 결과에 연결한다.

### Q39-06. 면접에서 User와 Employee를 분리한 이유로 알맞은 것은?

- ① 두 객체의 ID 숫자를 반드시 같게 만들기 위해서다.
- ② Employee에서 모든 비밀번호를 직접 검증하기 위해서다.
- ③ 계정 인증과 인사 정보의 책임·변경 주기가 다르기 때문이다.
- ④ 계정 권한 변경을 모든 부서 이름 변경과 함께 처리하기 위해서다.

**정답:** ③

**해설:** 인증 관심사와 업무 데이터의 생명주기를 나누면 변경 영향을 줄일 수 있다.

### Q39-07. 직원과 부서의 관계 설계에 대한 적절한 설명은?

- ① 직원마다 반드시 새로운 부서를 하나 생성했다.
- ② 여러 직원이 한 부서에 속하는 N:1이며 LAZY와 필요한 조회 전략을 함께 검토했다.
- ③ LAZY만 쓰면 모든 SQL이 사라지므로 조회 테스트를 생략했다.
- ④ 외래키 없이 이름 길이가 같으면 같은 부서로 처리했다.

**정답:** ②

**해설:** 데이터 관계와 실제 조회 비용을 함께 설명해야 설계 근거가 된다.

### Q39-08. 휴가 상태 관리에 대한 적절한 설명은?

- ① enum과 도메인 메서드로 PENDING에서 승인·반려하는 허용 전이를 검사했다.
- ② 자유로운 문자열을 요청자가 원하는 대로 저장했다.
- ③ Controller 응답의 색상만 바꿔 승인 상태를 표현했다.
- ④ 이미 승인된 휴가도 아무 권한 없이 반복 승인하도록 했다.

**정답:** ①

**해설:** 상태 모델은 허용 동작과 실패 조건을 코드로 보장하고 테스트로 확인한다.

### Q39-09. @Transactional을 적용한 이유에 대한 적절한 답변은?

- ① HTTP 요청을 무조건 관리자 요청으로 바꾸기 위해 적용했다.
- ② 모든 동시성 문제가 자동으로 해결되기 때문에 별도 검증을 하지 않았다.
- ③ HTML 출력 글꼴을 통일하기 위해 적용했다.
- ④ User·Employee 동시 생성과 승인 변경 같은 업무 단위의 원자성을 보장하기 위해 적용했다.

**정답:** ④

**해설:** 트랜잭션은 업무 변경의 함께 성공·실패를 보장하며 동시성 제어와 구분해서 설명한다.

### Q39-10. Entity 대신 응답 DTO를 사용한 이유에 대한 적절한 답변은?

- ① DTO는 모든 비밀번호를 자동으로 해시하므로 필드 검토가 필요 없기 때문이다.
- ② DTO를 반환하면 모든 DB 오류가 사라지기 때문이다.
- ③ Entity의 모든 관계와 비밀번호를 그대로 내보내기 위해서다.
- ④ 민감 필드 공개를 제한하고 지연 로딩·API 계약을 명시적으로 관리하기 위해서다.

**정답:** ④

**해설:** DTO 공개 필드는 직접 설계하며 조회·매핑 시점도 검증해야 한다.

### Q39-11. 관리자와 일반 사용자의 권한 구분에 대한 적절한 답변은?

- ① 신뢰할 수 있는 인증 역할을 서버에서 검사하고 자료 소유권·업무 가드를 함께 검증했다.
- ② 화면 버튼만 숨기면 직접 API 호출도 막힌다.
- ③ 요청 본문에 ADMIN이라고 쓰면 관리자로 처리했다.
- ④ 한 번 로그인하면 모든 사용자가 모든 자료를 수정하도록 했다.

**정답:** ①

**해설:** 역할 기반 인가와 개별 자료 접근 규칙을 코드와 권한 실패 테스트로 설명한다.

### Q39-12. 가장 어려웠던 문제의 해결을 설명하는 적절한 방식은?

- ① 오류를 경험하지 않았어도 해결했다고 주장한다.
- ② 실제 실패·원인 근거·수정·재검증과 배운 점을 연결해 설명한다.
- ③ 관련 기술 이름만 나열하고 결과는 생략한다.
- ④ 로그와 테스트를 모두 지운 뒤 문제가 없었다고 답한다.

**정답:** ②

**해설:** 검증 가능한 본인 사례를 짧은 흐름으로 설명하고 코드·커밋·테스트 근거를 제시한다.

### Q39-13. 사내 업무관리 시스템의 중요한 기능을 설명하는 적절한 기준은?

- ① 화면의 색상만으로 모든 업무 기능의 중요도를 정한다.
- ② 검증 없이 CRUD 개수만 많으면 충분하다고 답한다.
- ③ 권한·상태 전이·데이터 일관성이 연결된 업무 흐름과 사용자 요구를 근거로 설명한다.
- ④ 실제 요구와 관계없이 최신 기술 이름만 나열한다.

**정답:** ③

**해설:** 본인이 구현한 업무 흐름과 실패 방지 효과를 구체적인 근거로 설명한다.

### Q39-14. 승인·반려 기능에서 핵심 검증을 설명한 것은?

- ① 로그인 여부만 맞으면 모든 문서를 누구나 처리한다.
- ② 승인 버튼의 위치만 확인한다.
- ③ 반려 사유가 있으면 상태·행위자 검사를 생략한다.
- ④ 현재 상태, 처리 행위자·권한, 반려 사유 등 동작별 필수 조건을 확인한다.

**정답:** ④

**해설:** 허용된 사람의 허용된 상태 전이만 실행되도록 규칙과 실패 테스트를 연결한다.

### Q39-15. 공지 목록에서 페이징이 필요한 이유로 알맞은 것은?

- ① 조회량·응답 크기를 제한해 많은 공지를 효율적으로 탐색하게 한다.
- ② 페이징은 공지 작성자에게 관리자 역할을 부여한다.
- ③ 페이징을 쓰면 인증과 검증이 필요 없어진다.
- ④ 항상 전체 본문을 한 번에 보내는 것과 비용이 반드시 같다.

**정답:** ①

**해설:** 페이지 크기·정렬·검색을 실제 규모와 사용 흐름에 맞춰 설계한다.

### Q39-16. 전자결재 확장 계획에 대한 적절한 설명은?

- ① 요구 확인 없이 status 문자열을 무제한 추가한다.
- ② 다단계 결재·위임·감사 이력 등의 요구를 정하고 상태·권한·동시성·테스트 영향을 검토한다.
- ③ 이미 승인된 문서를 누구나 수정하게 한다.
- ④ 실제로 없는 확장 기능을 구현 완료라고 소개한다.

**정답:** ②

**해설:** 확장은 요구와 현재 구조의 한계를 근거로 계획하며 미구현 계획과 실제 결과를 구분한다.

## 6. 심화 노트 (면접 답변 포인트)

- **30초 답변 = STAR**: 상황(Situation)–과제(Task)–행동(Action)–결과(Result). 또는 더 짧게 "문제 → 해결 → 배움". 모든 답에 **"왜 그 선택을 했고, 대안과의 트레이드오프는 무엇인가"** 를 한 줄 넣으면 깊이가 산다(예: "EnumType.STRING 을 썼다 — ORDINAL 은 순서 변경에 깨지므로").
- **8대 단골 질문의 핵심 키워드**: ① 프로젝트 동기(SI 업무 흐름 학습) ② User/Employee 분리(라이프사이클·책임) ③ 부서 N:1 + LAZY ④ enum 상태 머신(PENDING→APPROVED/REJECTED) ⑤ @Transactional 위치(User+Employee 원자성, 승인 상태 변경) ⑥ Entity→DTO 분리(보안·직렬화·API 안정성) ⑦ 권한 다층(UserRole + @PreAuthorize + Service 가드) ⑧ 트러블슈팅 1건(4단계).
- **커밋 = "왜"만**: "무엇" 은 diff 가 보여준다. 한 커밋 = 한 의도(휴가+공지+결재를 한 커밋에 섞지 않기). 타입(feat/fix/refactor/docs/test/chore/style)을 일관되게.
- **PR 4섹션(무엇/왜/테스트/영향)** 이 채워진 PR 링크는 협업 역량의 증거다. 면접에서 코드보다 PR 을 먼저 보여주면 "혼자 짠 코드" 가 아니라 "리뷰 가능한 결과물" 로 보인다.
- **이 워크북 자체가 산출물**: 여기 채운 면접 답변·자기소개 문단·커밋 컨벤션을 그대로 `docs/` 와 README, 면접 노트로 옮기면 포트폴리오 문서 한 벌이 완성된다(22장과 연결).
